# Per-task subagent prompts — moved

The dispatched-subagent prompts moved into the engine at protocol 3, and the queue (protocol 5) keeps them there: they are **no longer read from this file at runtime**. Workflow scripts have no filesystem access, so the ten prompt variants now live as inlined template-builder functions in:

```
${CLAUDE_PLUGIN_ROOT}/skills/execute/task.workflow.js
```

The variants and the functions that build them:

| Variant | Builder in `task.workflow.js` | Returns (schema) |
|---|---|---|
| Implementer (gate off) | `implementerPrompt` | `IMPL_RESULT` |
| Read-only investigator | `readOnlyPrompt` | `IMPL_RESULT` (no PR) |
| Planner (gate on) | `plannerPrompt` | `PLAN_VERDICT` |
| Plan judge | `planJudgePrompt` | `PLAN_JUDGE` |
| Plan-reviser | `planReviserPrompt` | `PLAN_VERDICT` |
| Approved-plan implementer | `approvedPlanImplementerPrompt` | `IMPL_RESULT` |
| Review judge | `reviewJudgePrompt` | `REVIEW_VERDICT` |
| Reviser | `reviserPrompt` | `IMPL_RESULT` |
| Integrator (`mode: 'integrate'`) | `integratorPrompt` | `INTEGRATE_RESULT` |
| Integration judge (`mode: 'integrate'`) | `integrationReviewPrompt` | `INTEGRATION_REVIEW` |

Signatures are deliberately not reproduced here — read them off the script. The escalation parameters (`st`, the rung state, `prior`, `priorFeedback` — ADR 0006/0029) travel with the engine, and any copy of them in this file goes stale.

Sentinel strings (`PLAN-READY`, `BLOCKED:` and the old verified marker) are gone — every agent now returns a validated structured object (the `schema:` option on `agent()`), so the engine branches on typed fields instead of parsing free text.

The shared fragments (`BUG_PREFLIGHTS`, `GATED_INPUTS_CHECK`, `ralphLoop(...)`) carry the verifier-retry contract (since p31-1, estate ADR 0009 d1: `ralphLoop` runs the touched tests on each try and the verifier once, as the last check before the PR, and the one-shot `oneShotVerify` runs the verifier only when its touched tests are green; `fullSuiteLoop`, the old loop unchanged, is Integration's alone), the gated-inputs stop rule (ADR 0008 — spend/credentials/irreversible actions always stop the task call until signed (by Lachy, or for a covered spend gate or a declared test credential by the standing approval the lead applies after the stop, ADR 0034, ADR 0063); its predictive face is the plan's required `### Gated inputs` section, enforced by the plan-judge and paused on by the engine via `parseGatedInputs`/`unapprovedGates`; `GATED_INPUTS_CHECK` and the planner teach ADR 0038's one-line Cap (`spend: <what> — cap N USD`, its split in nested sub-bullets), and while `args.gatePricer` is set the plan judge prices each parsed spend gate through `gatePricingBlock`'s `exposure -` command, a gates-only `changes` bouncing once with no climb; once the gates are signed, an implementer or reviser stop for gates now all approved gets a same-rung continuation, its own prompt plus the static `SIGNED_GATES_RESUME` block via `pastSignedGates`, while each stop names a gate not yet passed at that site (a stop that repeats passed gates takes the old path), so `task.approvedGates` still never reaches a prompt), and the giflab-rollout bug preflights (dead code / no-op assertions / sibling-site blindness / worktree-safety) into every code-writing prompt. `GIT_ENV_SCRUB` and `GIT_ENV_RULE` carry the git-environment scrub (p12-3): every engine-rendered command that runs git or the verifier (the worktree setup, the verifier line, the preflights' git spans) starts with `unset $(git rev-parse --local-env-vars 2>/dev/null);`, and the rule (scrub every git or verifier command, never point a `GIT_*` location variable at the shared repository, test env isolation in a `mktemp -d` scratch repo) is in **every** agent prompt, the read-only task-tree agents and judges included, not only the code-writing ones. `RM_RULE` (p12-12, the 2026-10-01 stall) follows `GIT_ENV_RULE` in every agent prompt: remove a scratch directory by its literal path, or a `mktemp -d` one by its variable with no trailing slash or guarded (`${T:?}`), never a `cd` then a relative glob or an unguarded `$VAR/`, which Claude Code asks a person about even in bypass mode. `KILL_RULE` (p18-1, the 2026-10-04 incident) follows `RM_RULE` in every agent prompt: stop only a process you started, by its pid or process group, never by name or pattern (`pkill`, `killall`, `kill $(pgrep ...)`), because the lead, other agents and other sessions run the same verifier on the machine. The read-only agents (planner, plan judge, plan reviser, investigator) also carry `TASK_TREE_RULE` and enter the task's own tree with `taskTreeSetup` (ADR 0030, p12-4); the review judge is handed that tree as context only, with the PR authoritative. `args.verifySlot` (p23-4) is required (estate ADR 0009 d4): the engine refuses a call without it before any dispatch, in both modes. Every verifier line the engine renders is wrapped (`slotted`: the scrub, then `python3 '<verify-slot.py>' run --slots N -- bash -c '<verifier>'`, with `SLOT_TEXT` beside it; since p31-3 `SLOT_TEXT` tells the agent to wait for its verdict inside its turn, with the `wait` command that `run`'s first line names, never by ending the turn), the integrate call's line carries `--priority`, and the four `TASK_TREE_RULE` agents and the review judge carry `slotRule` (the exact wrapped line) right after `KILL_RULE`. **Touched tests** (p31-1, estate ADR 0009 d1): the full suite runs at two Checkpoints, the implementer's last check before its PR and Integration before the merge; every other verify runs the touched tests, which `touchedTests` tells an agent how to find (the rollout's optional `args.touched` pattern with `{module}`, read through `touchedOf`; else the repo's `CLAUDE.md`/`AGENTS.md` Tests line; else the test files importing the changed modules). The four `TASK_TREE_RULE` agents observe through `observeTests` (touched tests, and the verifier only when the task brief asks for a full-suite baseline); the review judge's tests block (`reviewTests`) checks a claim with touched tests in the task tree only when its read rule allows, and runs the verifier only when the brief asks the review for the full suite. A task call's `baselineManifest` rules out skipping the known reds from any run, touched or full; only the integrator's (`baselineManifest(a, true)`) still says to keep running the full verifier.

**The Flake check** (p29-9, ADR 0050): `FLAKE_CHECK_TASK` (built by `flakeCheck(DIFF_FILES)`) follows the verification block of every code-writing prompt (the implementer, the approved-plan implementer and the reviser), and `FLAKE_CHECK_INTEGRATION` follows `integrationVerify` in the integrator. Before a verifier red counts as red, the agent reads the failing tests' names: a red that names no test, one it cannot place in a test file or one in the diff is real at once; otherwise it re-runs only those tests by name with the repo's own runner, then the same verifier line once more on the same tree, green there being verified with each first-run failure a Flake. It returns them in the result's optional `flakes` field (`IMPL_RESULT` and `INTEGRATE_RESULT`: `[{ test, sha }]`), which the engine sanitises (`flakesOf`) onto the row's `flakes`, and never fixes one inside the task: reconcile logs each and files it for its repo.

Integration (ADR 0030 decision 3, p12-6) is the engine's second mode: `args.mode: 'integrate'` runs Integration's trouble path for one approved task. The integrator and the Integration judge enter the task's PR branch with `branchTreeSetup` (never a branch cut from the default branch), the integrator runs the rendered `integrationMergeStep` (which stashes tracked leftovers and pins the task's anchor, see `ANCHOR_RECIPE`), and the judge starts with `integrationJudgeCheck` and reads every first-parent merge since the anchor with `integrationMergeReads`. A seeded revise after an Integration rejection (`args.task.resume`) is the reviser with a COLD ENTRY block: it re-enters the tree through `branchTreeSetup`, fast-forwards it to `origin/<branch>` (a divergence is a STOP), never rebases or force-pushes, and writes no task note. Two diagnosis prefixes route a set-aside task: `integration: ` (it re-enters at Integration) and `REVISE_MARKER`, `revise: rejected at Integration re-review …` (it resumes as a seeded revise); a task-mode diagnosis that would read as either is written `own run: …`. Two named forms of `integration: ` (p27-4) are written only when the integrator's `blockKind` agrees with the merge step's own log: an Integration conflict (`integration: conflict unresolved in …`, then its resolution brief) and a verifier red (`integration: verifier red: …`); any other reason that would read as one is written `integration: set aside: …`.

To change a prompt, edit the builder in the workflow script.
