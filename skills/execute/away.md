# Away, the Trickle and the Away cap — how many Rollout tasks the Mac runs at once

By day, while Lachy is at the Mac, at most a few Rollout tasks run across the whole Mac, whatever the number of Rollouts: the **Trickle** (Chorus ADR 0104 d2). While he is **Away**, the **Away cap** bounds them: a larger Mac-wide cap, sized so suites do not contend, where each Rollout once ran to its own `parallel_ceiling`; each Rollout still runs within its own ceiling (ADR 0049, overturning Chorus ADR 0104 d3). Toward the Morning, a task starts only if it will finish by then: the **last starts** (Chorus ADR 0104 d4), and each night's held starts and overruns are recorded (§ The night record). Chorus says whether he is Away; this repo's queue keeps the count (Chorus ADR 0104 d6), so a Rollout run from a terminal obeys it too. Day or night, a hot Mac starts nothing new: the **Heat hold** (§ Heat, estate ADR 0009 d5). While Chorus's Capacity reading is fresh, its **Capacity** C takes the Trickle's and the Away cap's number, Legs count behind a Leg lease, and a lead whose Login is inside its line starts nothing new (§ Capacity, ADR 0067 d8).

thread-skill owns the state file below as its one reader: `next` (`skills/execute/scripts/reconcile-rollout.py`, `_away_state`) reads it on every call, `mark-started` reads it once per run for the Run record (§ Away), `status` reads it for its Trickle line and its last starts (§ The last starts: each queued row's `lastStart`, read with the history and never through `next`), and every progress line (`next`'s, `status`'s, and each `--rollout` verb's) reads it for the ETA's width (§ The Trickle). Nothing else here does, all of them read it silently, and only `next` prints the WARN. The lead never reads or writes it. Any writer may write it: Chorus does, and so may a person by hand (§ Without a writer). `next` also keeps one file of its own beside its note locks, the Trickle claims (§ The Trickle, *Trickle claims*), which only `trickle-wait` also reads, never writing. A second file, `~/.config/thread/capacity.json`, has its own readers (§ Capacity): `next`, `status`, every progress line, `mark-started`, `leg.py`, `verify-slot.py` and `lead-integrate.py` (its `verify --rollout` suite lines' `running`, through `mac_running`).

## The state file

The file is `~/.config/thread/away.json`, under the home dir as it is at the call (`Path.home()`), so a pinned HOME is the only override, as for `rollouts.toml` and `ladder.toml`. There is no env var and no flag.

It is one JSON object, read as at most 64 KiB of UTF-8. The first five keys are required and `away_cap` is optional. Extra keys are ignored, so a later field stays compatible.

| Key | Type | Meaning |
|---|---|---|
| `away` | a JSON boolean | True while Lachy is Away (Chorus ADR 0104 d1: the Evening, an Away block or the Lunch restart). |
| `until` | ISO 8601 with an offset or `Z` (a naive stamp is refused as ambiguous) | When this state is next due to change. Away: the Morning's hour, or the end of the Away block, that ends it. Not Away: the next Evening's hour, or the start of the next Away block. With no change scheduled: any time after the writer's next refresh. In both states a passed `until` reads stale. |
| `morning` | `"HH:MM"`, 00:00 to 23:59 | The Morning's hour, in local wall-clock time (the Mac's system time zone). `next` checks its shape and reports it, and reads it for the last starts (§ The last starts): an Away `until` on this hour is a night. |
| `trickle` | a JSON integer of at least 1 | N, the most Rollout tasks the Mac runs while not Away. A bool, a float, a string or 0 is refused: the Trickle is never 0 (§ The Trickle). |
| `written_at` | ISO 8601 with an offset or `Z` | When the writer last wrote the file. |
| `away_cap` | optional; a JSON integer of at least 1, strictly greater than `trickle` | A, the most Rollout tasks the Mac runs while Away (§ Away). A bool, a float, a string, null, 0, or a value at or below `trickle` is refused. Absent, the built-in applies (§ Away). Chorus writes it at every rewrite, Away or not. |

`away_cap` came after the other five (p29-8, ADR 0049). An engine snapshot from before it ignores it as an extra key and runs Away to each rollout's own ceiling (ADR 0043), so a writer may write it at any time, while such a rollout is live or paused.

A sample, Away overnight:

```json
{"away": true, "until": "2026-10-22T09:00:00+11:00", "morning": "09:00", "trickle": 2, "away_cap": 4, "written_at": "2026-10-21T18:00:00+11:00"}
```

The writer's duties:

- Write atomically: a temp file in the same directory, then a rename, so a reader never sees half a file.
- Rewrite it at each change of state, and rewrite it at least once every 24 h while a state holds (the same state with a new `written_at`). A long Away (a weekend) or a long day otherwise goes stale at 24 h and reads not Away at Trickle 2 partway through.

## Reading it

`next` reads the file once its refusals pass (a serial rollout, an incomplete one, an unresolvable ceiling), so a refused call reads nothing and prints nothing about it. `--now` is the reading's now, or the clock without it. The reading is one of four, reported as `trickle.file`, and `trickle.why` says why for every one but `fresh`:

| `file` | When | Reads |
|---|---|---|
| `fresh` | The object is well-formed and no stale test below holds. | `away` and `trickle` from the file, and the Away cap from its `away_cap` (else the built-in, § Away); `trickle.until` and `trickle.morning` are the file's. |
| `missing` | No file, a dangling symlink, or a plain file where `~/.config/thread` should be. | Not Away, Trickle 2. |
| `unreadable` | Any other read error (a directory at the path included), more than 64 KiB, not UTF-8, not JSON, not an object, a required key missing, or a key ill-typed (an `away_cap` at or below `trickle` included); `why` names the first problem, in the key table's order. | Not Away, Trickle 2. |
| `stale` | Any of the three stale tests. | Not Away, Trickle 2: the file's own `trickle` and `away_cap` are ignored. |

Every reading reports the Away cap as `trickle.awayCap`: the file's, or the built-in for a fresh file without the key, and the built-in 4 for the other three, which read not Away, so it never binds there.

The three stale tests, each a reader rule:

1. `until` is at or before now, in either state.
2. `written_at` is more than 24 h before now (exactly 24 h is still fresh).
3. `written_at` is more than 5 minutes after now. A writer whose clock runs ahead could otherwise keep a file fresh past its 24 h, so this one fails safe.

Only a fresh file sets `trickle.until` and `trickle.morning`; otherwise both are null.

A broken writer is loud. On `stale` or `unreadable`, `next` prints one line on stderr, on every call, `--dry-run` included:

`WARN: ~/.config/thread/away.json <stale|unreadable>: <why> — read as not Away, Trickle 2`

The line names the path as written here, never the resolved one, so it reads the same in every HOME and a lead can tell one line from another (execute § 4.5 step 1.1 prints each distinct line once per session). A missing file prints nothing: it is the documented default until a writer exists. A stale file warns too, because a working writer never leaves one: Chorus quit overnight, or a hand-written file passed its 24 h.

## The Trickle

While not Away, at most N Rollout tasks run across the whole Mac: N is a fresh file's `trickle`, else 2, and N is C while Capacity is in force (§ Capacity). `next` counts what runs elsewhere, then sizes this rollout's new starts to the room left; it never holds back a restart. While Away, the Away cap A takes N's place, counted the same way (§ Away), so every rule below holds for it too.

**The count elsewhere** (`trickle.elsewhere`). Off `--dry-run` it comes from a fresh walk of `--tasks-dir` (the one tasks dir every lead on the Mac uses), taken under the Trickle claim lock (*Trickle claims*, below); under `--dry-run`, from the walk `next` already makes. Another rollout note counts only when it sits directly in that dir (never under `Archive/`), is tagged `rollout`, is not `done` or `dropped`, is parallel, carries no `paused:` stamp, has started (an execute session's mark: the module docstring's "Never started"), and has no lapsed lease (**A lead's lease**, below). Its count is its linked notes at `status: in_progress`, less the ones its own undecided RACE or UNVERIFIED holds: `next` re-reads such a task as set aside, it never restarts, so it holds no Slot, and once Lachy's decision lifts the hold it counts again. A rollout draining a soft pause (`pause_requested`) still counts. Review and integrating notes never count, because Integration holds no Slot. This rollout counts its own the same way, every one of its `in_progress` tasks, live or stalled, never through `elsewhere`. The count is reported per rollout, `{<rollout>: n}` with n > 0 only, sorted. `next` adds another lead's live Trickle claims to that count (*Trickle claims*, below); `status` and every progress line count notes only.

**Serial rollouts are outside the count.** A Leg (`skills/execute/legs.md`) is one visible session working one task at a time, `next` never runs for a serial rollout, and a stopped Leg's claim stays `in_progress` with no session behind it, so counting it would hold the Trickle for nobody. While Capacity is in force (§ Capacity), a Leg counts behind its Leg lease instead, its claims or at least 1 from its session's start, which a dead Leg lets lapse.

**The limit** (`slotLimit`). Not Away, it is `min(ceiling, max(0, N − the count elsewhere − the places kept))`, the places kept being those a fair share keeps for waiting rollouts (*A fair share*, below). Away, it is `min(ceiling, max(0, A − the count elsewhere − the places kept))`, A the Away cap. A new start, a seeded revise (execute § 4.5 step 1.2) and a head Solo task's lone start all stop at it, counting every `in_progress` task of this rollout, live or stalled, as every other lead counts them: one fits while those tasks plus this call's starts (and, for a revise, the revises already launched) are below `slotLimit`, so not Away the room is N, less the count elsewhere, less the places kept for waiting rollouts, less this rollout's `in_progress` tasks, less this call's starts (Away, A in N's place). A running call is never stopped: `slotsInUse` may exceed `slotLimit`, as on the morning after an Away night, and then nothing new starts until the count falls.

**A restart waits on the ceiling alone.** A restart takes back a task whose note already reads `in_progress`, a task every other lead already counts, and Chorus ADR 0104 d4 says only that nothing *new* starts above the Trickle. So a restart is bounded by this rollout's `parallel_ceiling`, never by `slotLimit`, Away or not. Were it bounded there, a Login switch or a usage-limit respawn, which ends every background call, would leave each Cold-resumed lead waiting on the others' stalled notes with nothing running, every heartbeat reading the same until the Evening. A set-aside task handed back (an automatic retry, a recorded answer, a descope, a signed gate or `/thread:repair`) re-enters `in_progress` and restarts the same way, so a hand-back on a full Mac can take it past N (or A) by that one task; every lead counts it from the hand-back on.

**The hold.** A row held for want of a Slot reads `ceiling: <in use>/<ceiling> slots in use` once this rollout fills its own ceiling, else `trickle: <running>/<N> tasks running on this Mac` while not Away, or `away cap: <running>/<A> tasks running on this Mac` while Away, where running is `trickle.running` (below). While a fair share keeps places for waiting rollouts, either reads on with `, <k> kept for [[<rollout>]], …`, k the places kept and the rollouts in `trickle.kept`'s order (*A fair share*). Whichever binds first names the reason. Only a queued row ever reads `trickle:` or `away cap:`; a stalled one waits on the ceiling alone. A head Solo task the Trickle or the Away cap holds gets that reason, and the rows below it still read `behind solo [[…]]`. A whole-rollout (bare) git-env hold, or a main-red hold (`next`'s `mainRed`, a RACE revert that did not land), replaces every hold, and a pause holds its rows itself, so none of them ever reads `trickle:` or `away cap:`. A git-env trip that holds the lane only (ADR 0046) holds no Slot, so the Trickle and the Away cap read the rows as usual.

**It never halts.** A row the Trickle or the Away cap holds could start once the Mac has room, so while any row reads `trickle:` or `away cap:` the rollout is neither `stuck` nor `awaiting-sign-off`: `halt` stays null and the lead waits (execute § 4.5 step 1.6), even with nothing of this rollout in flight. A seeded revise the lead holds for want of `slotLimit` is no row of `next`'s, so `next` may read `stuck` over it; the lead's halt guard turns that `stuck` into the same wait (execute § 4.5 step 1.5). A rollout whose rows wait only on dependencies or gates halts as before, the cap full or not.

**The output.** `next` adds two keys after `slotsInUse`, every other key unchanged (`ceiling` included): `slotLimit`, an int, and `trickle`, `{away, file, why, limit, awayCap, until, morning, elsewhere, lapsed, running, kept}`, where `limit` is N, `awayCap` is A (reported in both states, binding only Away), `lapsed` is the rollouts a lapsed lease leaves out of the count, `{<rollout>: n}` with n > 0, sorted (below), `running` is the count elsewhere (another lead's live Trickle claims included) plus this rollout's `in_progress` tasks, live or stalled, plus this call's starts: the count every lead's cap sees once this call's starts are stamped, and `kept` is `{<rollout>: n}` for the places a fair share keeps for waiting rollouts, n > 0, sorted, `{}` when none (*A fair share*). The Run record's `idle-slots` event reads `hold-trickle` whenever the call holds a row on `trickle:`, and `hold-away-cap` whenever it holds one on `away cap:`; its `free` stays the ceiling's.

**A fair share.** A lead re-runs `next` the moment one of its calls returns, so a rollout already inside the Trickle would refill every place it frees, while a rollout waiting on the Trickle re-checks only at its heartbeat's tick or when its trickle wait returns, never the moment a place frees. So `next` keeps a freed place for the rollout waiting on it, in turn, and every lead keeps it alike.

- *The waiting record.* Off `--dry-run`, under the Trickle claim lock and in the same write as its claims (*Trickle claims*, below), `next` records its rollout as waiting whenever its final holds include a row on `trickle:`, `away cap:` or `heat:` (so a hot spell keeps a rollout's place in line), or a seeded revise waits on `slotLimit` (*A seeded revise contends*, below): one record in `trickle-claims.json`'s `waiting` list, `{tasksDir, rollout, since, at, served, want}`. `tasksDir` is the tasks dir's real path and `rollout` the rollout's stem. `since` is when it began waiting, carried from its own earlier record, else now. `at` is the call's now, to the second. `served` is now once the call starts a task, else the later of its own earlier record's and the rollout's latest `started:` stamp (the § 4 stamp: the first start wins, so a restart or a revise never moves it), else null, never served: so a start whose call wrote no record (one that could not take the lock) still moves it. `want` is how many places it waits for: its waiting rows other than a head Solo task, or with none, 1 for that task's lone start while nothing of the rollout is in flight, started or owed a revise, plus the seeded revises step 1.2 cannot launch under `slotLimit`, capped at the room its own ceiling leaves once the ones it can launch are counted (no record at 0). Each call replaces its rollout's earlier record, and a call with nothing waiting (everything started, a pause, a rollout hold, main red or a whole-rollout git-env hold) removes it.
- *Reading the records.* A waiting record lives 30 minutes from its `at`, to the second: a lead that is gone holds its place for nobody until then. `next` reads the list in this order. A malformed record (not an object, a key missing, a time that is empty or does not parse, a `want` that is no whole number of at least 1, or a `since` or `served` after its `at`) is dropped silently. One of another tasks dir is never counted, and kept only while under 30 minutes old by the real clock. One 30 minutes old or more, or as far ahead of now, is dropped. Of repeats for one rollout, the latest `at` wins. Only then is the caller's own taken out, its `since` and `served` carried: so a lapsed or future own record is never read, its rollout's `since` starts again at now and its `served` falls back to the `started:` stamps. A record whose rollout note is present but outside the count (under `Archive/`, closed, serial, paused or untagged) keeps nothing, and one whose rollout note is missing from the walk keeps its place until it lapses, under the name it recorded. A never-started rollout's record counts like any other: that is the morning launch.
- *The allocation.* While the Mac has free places (the cap, less the count elsewhere, less the caller's own `in_progress` tasks) and is not hot, `next` gives them out one at a time among the waiting rollouts and the caller: each goes to the one that holds fewest, then was served least recently (never served first), then has waited longest, then by stem, and the winner then holds one more and reads served now. A waiting rollout asks for its `want`. The caller asks for what it could start now within its own ceiling: its queued rows whose dependencies are met, ranked above its head Solo task, or with none above it that task's lone start while nothing of it is started or owed a revise; none under a pause, a rollout hold, main red, a whole-rollout git-env hold or a started Solo task. To those it adds its seeded revises (*A seeded revise contends*). `slotLimit` leaves out the places the others win; the caller keeps the rest.
- *A seeded revise contends.* A seeded revise (execute § 4.5 step 1.2) is no row of `next`'s, yet it takes a Slot under `slotLimit` like a new start, so `next` counts the revises step 1.2 launches in the caller's demand and in its record's `want`, and `next` claims the ones step 1.2 launches (*Trickle claims*): a rollout whose only work is a revise still gets its place in line, under *The bound*. It reads each set-aside task as step 1.2 does: set aside at its run, `blocked`, no task `hold_until` standing, `lead-integrate.py inputs` reading `autoRevise: true` under the `max_review_rounds` a call resolves (the task's, the rollout's, then `rollouts.toml`), a `pr:` the engine takes (read against the Project root, the lead's `--repo`) and no recorded answer. None counts under a pause, a rollout hold, main red or a whole-rollout git-env hold, where step 1.2 launches none, and a task it cannot judge (a round budget that does not resolve, a `lead-integrate.py` that will not load) counts as none and never fails the call. A revise the rollout's own ceiling holds is never waited for. Being no row, it still leaves `next` reading `stuck` over a rollout whose only work is a revise; the lead's halt guard turns that into the same wait (execute § 4.5 step 1.5).
- *The hold.* A row the kept places hold reads `trickle: <running>/<N> tasks running on this Mac, <k> kept for [[<rollout>]], …` (Away, `away cap: …`), and `trickle.kept` reports `{<rollout>: n}`. It never halts, like any `trickle:` or `away cap:` hold, and the lead's steps are unchanged. Under the heat nothing is kept: `slotLimit` is already 0, the rows read `heat:` with no suffix, and every record keeps its place in line until the Mac cools.
- *The bound.* A waiting rollout W that holds no place is passed over by at most R − 1 freed places, R the rollouts contending. Only a rival holding no place and served less recently than W can go first, a never-served rival only if W is never served too and the rival began waiting earlier, and each such rival goes first at most once, since once served it sorts behind W. A seeded revise, like a restart, moves no `served` (the task's `started:` stamp is its first start's), so a rival whose place went to a revise can go first once more: each seeded revise a rival launches while W waits adds at most one freed place to that bound. A morning launch is never served, so only older never-served waiters precede it. Once W is first in line, every lead's `next` keeps the next freed place for W, and W starts at its own next `next`: within one trickle-wait poll (20 seconds) and its lead's turn once a lead on this engine keeps the place while W's trickle wait runs, else within one heartbeat tick (20 minutes) of that place freeing. A heat-held W, whose turn launched no trickle wait, has only the tick's bound (*What does not wake it*). A start or a seeded revise never takes the count past N (or A): the share only ever lowers `slotLimit`.
- *The cost.* A kept place stays empty until the waiting lead's trickle wait returns (one 20-second poll and its turn), or where no wake comes or none is read (a giver on an older snapshot, a place freed with no giver `next`, a heat-held waiter: *What does not wake it*) until its next tick (up to 20 minutes), or until its record lapses (30 minutes) if that lead is gone. Fairness counts tasks, not time: a rollout with long-running tasks keeps its count until they return. Restarts are exempt: a restart waits on the ceiling alone (above). A seeded revise is not: `slotLimit` bounds it like a new start, so it yields to a place kept for another rollout, and it contends for a place of its own like a queued row (*A seeded revise contends*). A rollout whose only work is a revise therefore waits under *The bound*, and once a place is kept for it, step 1.2 launches the revise at its lead's next step 1: within one trickle-wait poll and its turn of the place being kept, else within 20 minutes.
- *Mixed snapshots* (ADR 0043). An engine snapshot from before p28-5 reads only `claims`, keeps nothing and drops `waiting` when it rewrites the file. Its waiting leads re-record at their next tick, keeping `served` (from their `started:` stamps) and losing only `since`, so fairness is only as good as the share of leads on the new engine.
- ***A waiting lead re-checks sooner* (p28-9).** A kept place would otherwise stand empty until the waiting lead's next heartbeat tick, so the lead that keeps it wakes the waiting one.
  - *The wake.* Off `--dry-run`, in the claims write (*Trickle claims*, below), a `next` whose `trickle.kept` is not empty writes one wake per kept-for rollout into `trickle-claims.json`'s `woken` list, `{tasksDir, rollout, at, by}`: the tasks dir's real path, the kept-for rollout's stem, a time to the second and the giver's stem. `at` is the later of the giver's now and the kept-for rollout's waiting record's `at`, so a wake is never older than the record it answers, whatever order two calls took the lock in. It replaces an earlier wake for that rollout. A giver keeping the same places again rewrites only the wake's `at`: one claims write per such call, an accepted cost. A wake lives 30 minutes from its `at` and is read as the waiting records are (malformed dropped silently, another tasks dir's kept by the wall clock and never matched, the latest `at` per rollout winning). The rollout's own `next` consumes it: any write of its own drops it. `--dry-run`, a lock not taken, a failed write, a file of another version and the heat (nothing is kept) write none.
  - *The trickle wait* (`reconcile-rollout.py trickle-wait --rollout <note>`, execute § 4.5 step 1.6) reads `trickle-claims.json` every 20 seconds, takes no lock and writes nothing. Its baseline is when its lead last looked: its own waiting record's `at`, or its last `next`'s lease (`by: next`) if later, never a `record-entry`'s (`by: entry`, written at every loop entry and heartbeat tick), and it never moves back within one wait. It exits 0 on a wake for its rollout at or after the baseline (`trickle wait: a place is kept for [[<rollout>]] by [[<by>]]`), 3 with nothing to wait for (no live waiting record of its own, an unreadable file or another version: `trickle wait: nothing to wait for: <why>`), 75 after 1200 seconds (`trickle wait: no place kept for [[<rollout>]] within <n> s`), and 2 on usage.
  - *The lead's routing.* On 0 or 75 the lead runs step 1. On 3 it starts nothing and the heartbeat is the backstop, so a `next` that cannot write its record never loops turns; one whose lock failed still writes its lease (`by: next`), so the wake it already saw never fires again.
  - *Why 1200 seconds.* The wait launches at a turn's end, while the record's `at` is that turn's first `next`: 1200 seconds plus a long turn stays under the record's 30-minute life, so a lead whose calls are in flight refreshes its record before it lapses.
  - *Why `version: 1`.* The file stays at `version: 1`: p28-5's `waiting` widened it the same way, and a reader from before p28-9 ignores `woken`. There is no ADR of its own: it is a tuning inside Chorus ADR 0104 (and ADR 0049), as the fair share is.
  - *Why not a shorter heartbeat.* Each `*/5` tick is a full lead turn whose `next` takes the trickle claim lock and walks the tasks dir: four times the idle turns of the `*/20` tick alone. The wait costs more than its small file read every 20 seconds: its timeout (exit 75) sends the lead to step 1 every 1200 seconds, a full turn whose `next` runs off `--dry-run`, takes the lock and walks the tasks dir, while the `*/20` tick's *Cold resume* (clause 7) still runs `next` too. So an idle Trickle-waiting lead with nothing in flight takes about two such turns per 20 minutes, twice the tick alone's, against four times for `*/5`, and only the wait answers a kept place within 20 seconds.
  - *What does not wake it.* A lease lapse, a hand pause, a set-aside or a cooling Mac frees a place with no giver `next`, and those wait for the tick. A heat-held waiter misses even a giver's wake: step 1.6 launches no trickle wait on a `heat:` row or a heat-held revise, yet its `next` still writes its waiting record (*The waiting record*), so once the Mac cools a giver's `next` keeps it a place and writes the wake with no wait running to read it (unless one an earlier Trickle-held turn launched still runs). It starts only at its tick, or, with calls of its own in flight, only when one of them returns.
  - *Mixed snapshots* (ADR 0043). A snapshot from before p28-9 writes no wake and drops `woken` when it rewrites the file, so its waiter re-checks at its trickle wait's timeout or its tick. Its own leads never launch a wait, and wakes written for them lapse at 30 minutes.
- *Why not a first start, or a sooner re-check alone.* One start past the Trickle per launch would break Chorus ADR 0104 d4 (nothing new starts above the Trickle) and its rejected *A Trickle per Rollout*, and the promise that a start never takes the count past N. A sooner re-check alone would not do: a refilling lead re-runs `next` as soon as its call returns, so it wins every race. The fair share settles the race; the trickle wait only shortens the idle kept place.

**The ETA.** The progress line's rough remaining estimate (p28-6) counts its chunks at the Trickle's limit, `min(ceiling, max(1, cap - the count elsewhere))`, the count elsewhere read from the notes only (no Trickle claims) and the cap in force by Away state: `slotLimit` floored at 1 (a full Mac still drains one at a time) and with the Heat hold and a fair share's kept places left out (both pass). `status`'s `timeline` reports it as `etaWidth`, with `etaBy` `ceiling`, `trickle` or `away cap`. `status` also reports the `trickle` block itself, read the same way from the notes only, plus `here` (this rollout's own count as the others read it, 0 while its own lease has lapsed) and `lease` (its own lead's lease, `{state, writtenAt, lapsesAt}`), for its Trickle line; it writes no lease.

**A morning launch still starts** (Chorus ADR 0104 d2) is read as the Trickle is never 0: N is at least 1. It does not mean a new rollout starts at once: night work still drains above the Trickle (d4 lets it finish). It does mean a bounded wait once places free: a morning launch records itself waiting like any rollout, never served, so the fair share passes it over only for rollouts that began waiting before it and were never served either, and it starts within one trickle-wait poll and its lead's turn of the place kept for it while its trickle wait runs (else within one heartbeat tick, as after a heat-held turn: *What does not wake it*), never behind whoever refills first (*A fair share*).

**Trickle claims.** Two leads' `next` calls would otherwise both see the room one free place leaves, from one lead's `next` to its § 4 stamp, and the heartbeat's ticks bring waiting leads back together. So off `--dry-run`, once its refusals pass and every PR hold is read, `next` takes the machine-wide `trickle.lock` in the note-lock dir (`THREAD_NOTE_LOCK_DIR`, else `$XDG_STATE_HOME/thread/note-locks`, else `~/.local/state/thread/note-locks`), walks `--tasks-dir` afresh, counts and picks its starts. Once the rollout note's own save has succeeded, it records one claim per start (the head Solo task's lone start included) and one per seeded revise step 1.2 launches (execute § 4.5 step 1.2: the first of its seeded revises, in `next` order, while `slotsInUse` plus the ones before it is below `slotLimit`) in `trickle-claims.json` beside the lock, replacing its rollout's earlier claims, and lets the lock go; a call whose save fails claims nothing. A claim names the tasks dir (its real path), the rollout, the task and `at`, the call's now to the second; a revise claim also carries `kind: revise`. Every other lead's `next` counts a live claim under its rollout in `trickle.elsewhere`, beside that rollout's notes; a lead's own claims never count against its own rollout.

- A claim is consumed by its task's § 4 stamp. It counts until the note-based count counts that task (`status: in_progress`, and the rollout started), so a stamp written in two edits, in either order, never drops it and never counts the task twice. A task that leaves the queue another way (set aside, in review, done) drops a start's claim. A revise claim counts while its task is set aside at its run, `blocked`, with no recorded answer, or while it runs until the note-based count counts it; it drops at once when the task is handed back, answered, in review or done, or set aside at a gate or at Integration. A revise's note already carries `owner:` from its first start, so the status edit alone counts it, and either order counts it once.
- A claim lives 20 minutes from its `at`, to the second: one heartbeat tick. A lead that never stamps holds that room for nobody until then: a crash, or a refusal after a successful `next` (a § 2.5 or canary refusal at step 1.3), a bounded cost. For a revise, the one-off causes are a crash, a § 2.5 refusal, a `verifySlot` halt or an `inputs` exit 2 that halts (execute *lead-integrate's exit 2*), at step 1.2 before its stamp. A lock holder that dies frees the lock with its process.
- A claim counts only in the tasks dir it was written for. One whose task note is missing from the walk still counts (a note caught mid-edit fails to parse and is skipped), and so does one whose rollout note is missing from the walk (torn mid-edit, or deleted), under the name the claim recorded, until it expires. One whose rollout note is present but outside the count (under `Archive/`, closed, serial, paused or untagged) counts nothing and goes at the next write, as does one whose task note now names another rollout or has left the queue another way.
- `--dry-run` reads the claims against the walk it already makes and writes nothing, taking no lock. A pause, a rollout hold, the heat, a whole-rollout git-env hold (a bare checkout, `gitEnvHold` `scope: rollout`) or a main-red hold (`mainRed`, a RACE revert that did not land) leaves the call's `start` empty, which clears its rollout's claims. A pause, a rollout hold, main red or a whole-rollout git-env hold also claims no revise (step 1.2 launches none), and neither does the heat (`slotLimit` 0). A git-env trip that holds the lane only (ADR 0046) leaves `start` as it is, so its starts and seeded revises are claimed as usual.
- It fails open, never a halt: each failure prints one line on `next`'s stderr, which execute § 4.5 step 1.1 relays, and the call carries on. A lock it cannot take or a write that fails leaves the call's own starts and seeded revises unclaimed, the old window, and writes no waiting record either (*A fair share*). An entry it cannot read (not an object, a key missing or empty, an `at` that does not parse or cannot be placed in local time, or a `kind` that is present and not `revise`) is dropped silently: it counts nothing and the next write leaves it out.
  - `WARN: trickle claims <lock path>: <why> — counted without the lock; this call's starts are not claimed`: a lock not taken within `THREAD_NOTE_LOCK_TIMEOUT` seconds (30), or a lock dir it cannot write. The count still runs, reading the file without the lock.
  - `WARN: trickle claims <path> unreadable: <why> — read as none`, `--dry-run` included: over 256 KiB, not UTF-8, not JSON, not an object, no integer `version`, or `claims` not a list. The next write replaces it. A `waiting` that is no list reads as no record, and a `woken` that is no list as no wake, with no WARN, and the next write replaces it too.
  - `WARN: trickle claims <path> version <v> — read as none, left for its writer`: the file is `{"version": 1, "claims": […], "waiting": […], "woken": […]}` (a file in p28-3's shape, with no `waiting`, reads as no record, and one in p28-5's, with no `woken`, as no wake), and one of another version is never written.
  - `WARN: trickle claims <path>: <why> — this call's starts are not claimed`: the write failed.
- An engine snapshot from before p28-3 (ADR 0043) neither reads nor writes the file, so its starts keep the old window, one call's starts per lead. An engine snapshot from before p28-8 keeps only a claim's four keys, so it reads a revise claim as a start claim on a task set aside: it counts nothing for it and leaves it out of its next write. While such a lead shares the Mac, a revise's claim lasts only until that lead's next `next`: the old window for the leads that read the file after it.
- A seeded revise (execute § 4.5 step 1.2) is claimed the same way, by `next`, while the lead's own steps stay as they are. `next` reads each set-aside task as step 1.2 does (*A seeded revise contends*) and claims the ones step 1.2 launches under `slotLimit`. Its § 4 stamp consumes the claim, and it lapses in 20 minutes like any claim. Step 1.2 still judges each revise itself, so the two can differ:
  - *One-off causes.* A revise `next` claims but step 1.2 does not launch because of a crash before the stamp, a § 2.5 refusal, a `verifySlot` halt or an `inputs` exit 2 that halts holds that room for nobody until its claim lapses, as an unstamped start does.
  - *A lasting disagreement.* Suppose step 1.2 keeps declining a revise because its own `inputs` reads `autoRevise: false` under § 3's `max_review_rounds`, where `next` read it true under the round budget it resolves. That revise is claimed again, with a fresh `at`, at each `next` of that lead. It holds one place on the Mac for nobody for as long as the disagreement lasts and the lead keeps ticking. Before p28-8, that disagreement shaped only its rollout's own demand and `want`.
  - *Changes only the owning lead reads.* A task `hold_until` set, a `pause_requested`, a `pr:` or round-budget edit, or an undecided RACE or UNVERIFIED on the task keeps the claim counting until that lead's next `next`, which claims it no more, or until it lapses. A recorded answer, or a `paused:` stamp on its rollout, drops it at once.
  - *A launch `next` did not claim* (one `next` could not judge, or read otherwise) keeps the old window from its launch to its stamp.
  - *The over-count.* The call before step 1.2 claims both its `start` and the revises step 1.2 will launch, although both draw on one room. Step 1.2 launches its revises first, and its re-run of `next` replaces the start claims with fewer. For those seconds, other leads count up to that many places more than this rollout will use. That is an over-count, never an overshoot. But a lead whose `next` reads it in that window acts on it until its own next `next`: its rows wait on `trickle:` (or `away cap:`), it records itself waiting, and the place the re-run frees is kept for it (*A fair share*) and stays empty until its trickle wait reads the re-run's wake (one 20-second poll and its turn: *A waiting lead re-checks sooner*), or where no wake comes or none is read (*What does not wake it*) until its next tick, up to 20 minutes.

**A lead's lease.** The count reads notes, never sessions, so each live lead keeps a lease: `~/.config/thread/leases/<rollout>.json` under the home dir at call time, `{rollout, written_at, by}`, plus `login`, the lead's Login, when it runs in a Claude Code session (ADR 0067 d8: § Capacity, *The quota hold*). `next` rewrites it on every call off `--dry-run` once its refusals pass (a refused call, a serial note and a superseded one write none), and `record-entry` at every loop entry and every heartbeat tick (execute § 4.5 *Run record*), before it reads the Run record. Each write goes through a temp file and a rename, so a reader never sees a torn lease; one it cannot make prints one `lease: warning: cannot write ~/.config/thread/leases/<rollout>.json: <why>` line on stderr and changes nothing else (execute § 4.5 step 1.1 relays it). A lease lapses 45 minutes after its last write, or after the Mac's latest boot or wake if later: two heartbeat ticks and five minutes, so one late or missed tick never lapses a live lead, and a sleeping Mac lapses nobody (a boot or wake counts only when it is after the last write and at or before now; exactly 45 minutes still holds). A rollout whose lease has lapsed leaves every other rollout's count, and `trickle.lapsed` names it there instead, so a lead that is gone (its session closed, or a § 7 halt left stalled rows: a git-env halt does, and deletes the heartbeat, so no tick re-enters it) holds room for nobody no longer than that. Only its notes leave: a live Trickle claim of its still counts (*Trickle claims*, above), since the `next` that wrote the claim renewed the lease first, so a claim outlives its lease only when that lease write failed. A standing room stop keeps it: a room stop under its 6 h bound (execute § Room stop item 11), the Stage's usage-limit wait included, keeps a lapsed lease counting, since its calls resume with the Stage; a held one past that bound, which `step-boundary.py stands` still reads standing while the Stage lives, keeps it no longer, so a hold that waits days for a weekly reset holds no room on this Mac meanwhile. A rollout with no lease file still counts, and so does one whose lease is unreadable (a directory at the path, over 4 KiB, not UTF-8, not a JSON object, or a `written_at` missing, ill-typed, naive or more than 5 minutes ahead), so a broken lease fails toward the count. An engine snapshot from before p28-4 writes none (ADR 0043), so its remedy stays Lachy's: `trickle.elsewhere` names the rollout, and stamping it `paused:` (execute *Pausing + reinstating a rollout*: the hard pause's first step, its calls already dead) takes it out of the count at once; its reinstate, `/thread:execute [[<rollout>]]`, restarts its stalled tasks and they count again. A lead that comes back counts again from its first `record-entry` or `next`, before any restart. Its residuals: a usage limit the Stage did not announce, or one off the Stage; a Codex session-driven `--gated` run, which has no heartbeat (execute *Native runtime binding*), whose merge hold waits past 45 minutes on Lachy, or any Codex stretch that long with no `next` or entry; and a § 7 halt that leaves calls in flight. Each lapses a lease while calls may still run: other leads may then start into that room, and the returning lead's restarts can take the Mac past N (or A) until the count falls, the overshoot a hand-back already allows.

## Capacity

ADR 0067 d8: one Mac-wide **Capacity** bounds parallel task starts, Leg task claims and full suites, set by how much the Mac can take now. Chorus measures and writes it (chorus-p96-28); thread-skill reads it, so a rollout run from a terminal obeys it too. The reader is `skills/execute/scripts/capacity.py`, the one copy of this section's constants; `reconcile-rollout.py`'s `_capacity_state` adds the maximum, and `capacity_gate` is a Leg's arithmetic. It **replaces the Trickle's number, never its machinery**: while a reading is in force, C is the Mac-wide cap `next` applies, N by day and A while Away, and the Trickle claims, the claim lock, the fair share, the wakes, the leases, the last starts and the hold prefixes `trickle:` and `away cap:` stay exactly as above. Anything but a reading in force falls back to today's Trickle and Away cap, exactly, never to open.

**The file.** `~/.config/thread/capacity.json`, under the home dir at call time (a pinned HOME is the only override), one JSON object read as at most 64 KiB of UTF-8. Extra keys are ignored.

| Key | Type | Meaning |
|---|---|---|
| `capacity` | required; a JSON integer of at least 1 (a bool, a float, a string or 0 is refused) | The Capacity Chorus suggests now. |
| `written_at` | required; ISO 8601 with an offset or `Z` (a naive stamp is refused) | When the writer last wrote the file. |
| `signals` | optional; a JSON object | What Chorus measured (load, memory, thermal, suites). Read for `stop_suites` and `memory` only (*Full suites*, below): `stop_suites` JSON `true` (Chorus sets it at memory critical, `memory` 4, or at thermal trapping) holds and stops slotted suites, and any other value is no stop; `memory` (an integer: 1 normal, 2 warning, 4 critical) names the stop's label and, after a Capacity stop, holds that run's restart at warning (2) or worse. Neither ever makes the file unreadable. |
| `logins` | optional; a JSON object keyed by Login name, each value `{inside_line: bool, why?: string}` | Which Logins are inside their usage line now (the quota hold, below). An ill-typed `logins` makes the whole file unreadable. |

**Login names.** A `logins` key is a Chorus Login name: Chorus keeps a Login's name as its key for good (`src/stage/logins.py`), its primary is `dummy`, and every session it starts carries `CLAUDE_ACCOUNT_PINNED: <name>` (a hand-started one derives it from `CLAUDE_CONFIG_DIR`'s basename, else `dummy`, in `~/.zshenv`). So the caller's Login is read only in a Claude Code session (`CLAUDE_CODE_SESSION_ID` set: the shell sets the pin in Codex shells too, so a Codex or any other caller is never held), as the first of: `CLAUDE_ACCOUNT_PINNED`, stripped and non-empty; `CLAUDE_CONFIG_DIR`'s basename, a trailing slash stripped; else `dummy`. A name the file does not list is never held.

**The readings**, reported as `trickle.capacity.file` with `why` for every one but `fresh`:

- `fresh`: well-formed, and `written_at` neither more than 10 minutes old (exactly 10:00 is still fresh) nor more than 5 minutes ahead of now (exactly 5:00 is still fresh);
- `missing`: no file, a dangling symlink, or a plain file where `~/.config/thread` should be: silent, the documented default until a writer exists;
- `unreadable`: any other read error (a directory at the path included), over 64 KiB, not UTF-8, not JSON, not an object, a required key missing, or a key ill-typed; `why` names the first problem in the key table's order;
- `stale`: `written_at` past either bound.

**The writer's duties.** Write atomically (a temp file in the same directory, then a rename), and rewrite the file at least every 2 minutes, a state that holds included, so a working writer never leaves it stale. "Away raises its target" is the writer's: the reader only clamps.

**In force, and C.** A reading is in force only while it is fresh and `capacity_max` resolves: the hard maximum, a machine-wide `[defaults]` key of `~/.config/thread/rollouts.toml` (execute § 3's settings table: built-in 6, minimum 1, schema 4), read through `rollout-settings.py`. Then **C = min(max(capacity, 1), capacity_max)**. On `stale` or `unreadable`, and on a fresh file whose `capacity_max` will not resolve (a refused rollouts.toml, no tomllib), `next` prints one line on stderr, on every call, `--dry-run` included, and reads the Trickle:

`WARN: ~/.config/thread/capacity.json <stale|unreadable>: <why> — read as the Trickle`

`WARN: ~/.config/thread/capacity.json capacity_max unresolved: <why> — read as the Trickle`

execute § 4.5 step 1.1 relays each distinct line once per session, as it does away.json's. `next` reports the reading as `trickle.capacity`, `{file, why, suggested, max, maxSource, maxWhy, limit, inForce, quota}` (`limit` is C, null when not in force), and while it is in force `trickle.limit` and `trickle.awayCap` read C. `status` reports the same block, read silently and without the quota. Every progress line's ETA reads C as its cap, and `mark-started`'s slot-taken `cap` is `{away, n: C, file, by: "capacity"}`, so a Reflection never reads a Capacity's number as the Trickle's. C below what already runs (the Morning, a halving on a yellow signal) stops nothing: `slotsInUse` may exceed `slotLimit`, and nothing new starts until the count falls. Away still sets the prefix (`away cap:`) and the last starts.

**Legs and the Leg lease.** While Capacity is in force, the count elsewhere also counts each open serial rollout's Leg claims, and so does the Run record's suite `running` (suite-started and suite-ended, `mac_running`, p36-9: the count C bounds; under the fallback it stays parallel-only): its `status: in_progress` rows owned `leg-<n>`, behind its **Leg lease**, the same `~/.config/thread/leases/<rollout>.json` a lead keeps, with `by: "leg"` and `waiting: true` when a `next --waiting` wrote it. It lapses 90 minutes (LEG_LEASE_LAPSE) after its last write, or 180 minutes (LEG_WAIT_LAPSE) for a waiting one, counted from the Mac's latest boot or wake if later, as a lead's lease is. A fresh or unreadable Leg lease counts (one more than 5 minutes ahead reads unreadable), and a fresh one counts at least 1, so an open Leg holds a place from its session's start, `begin` included, not from its first claim (ADR 0076 d3; its first claim still counts 1, never 2); a lapsed one leaves the count and `trickle.lapsed` names it; none holds nothing, so a Leg on an older snapshot, which writes none, is uncounted. leg.py writes it on its own open Leg, never under `--dry-run`: `begin` (a fresh Leg, a take-over, `--resume` and a silent resume), `next` (only the Leg's own session, both ids known and equal), `claim`, `wait`, `smoke`, `done`, `set-aside` and `land`; `close`, any outcome, deletes it, so a stopped or halted claim holds no place while no Leg runs it. legs.md names the renewal points: `leg.py next` before each re-run of a verify-slot wait, the review's `next --waiting` turn end (its 180 minutes cover a checker's slot wait) and `next` first when its notification arrives, and `next` in any stretch over an hour with no leg.py call. Under the fallback Legs stay out of the count and a Leg claims as before.

**A Leg's claim.** While Capacity is in force, a Leg's `next` turns a `claim` (a fix task's included) that has no room into a `wait` of kind `capacity` (why its `trickle: <r>/<C> tasks running on this Mac[, <k> kept for …]`, `away cap: …` or Heat hold line, § Heat) or `quota` (why `quota: <login> is inside its line`). The room is C, less the count elsewhere (parallel notes, live Trickle claims, counted Legs), less the places the fair share keeps for other waiters, less this chain's own places: its claims, or 1 for its session while its Leg lease reads fresh, as every lead counts it, so a session's first claim needs no new place and a place every lead counts as this Leg's is never kept for a rival that could not use it (p44-2). Waiting Legs with no claim take turns: a Leg leaves out of its count another Leg counted for its session alone whose waiting record waits behind its own (a later `since`, then a higher stem; a Leg with no record of its own reads `since` now), so of more waiting Legs than places (C halved under swap) the ones waiting longest claim and none stands still counting the others; a Leg that is not waiting, or has a claim, always counts, and `next` counts every Leg's session. A `finish` (own or inherited), a `handoff`, `complete`, `stuck` and a rank `wait` pass untouched, and so does every plan under the fallback. `claim` re-checks under the trickle claim lock, taken inside the Leg's rollout lock and rank lock around only the recount, the Leg lease, the task note's save and the claims write (never git, gh or a child process: the heat, the Mac's boot and wake and the Capacity and Away readings are read before it, so a lead's `next` never waits on a Leg's git or a reading): no room writes the chain's waiting record and stands exit 3, nothing written to the notes; room writes the lease, saves the note, then drops its record and wakes. A lock not taken in 30 seconds is exit 5, never an unlocked claim. A waiting Leg's record keeps its place in line while its Leg lease reads fresh or unreadable, so every lead keeps it a place in turn (§ The Trickle, *A fair share*), asking one place fewer while its session is counted (its place then is that session's, held once, never kept again); its `leg.py wait` polls every 15 seconds and re-records every 10 minutes, under a record's 30-minute life.

**The quota hold.** While Capacity is in force and the caller's Login is inside its line, the caller starts nothing new: for a lead, no start, no seeded revise and no head Solo task (`slotLimit` 0); for a Leg, no fresh claim. Restarts and a Leg's `finish` wait on the ceiling alone. A row it holds reads `quota: <login> is inside its line`, after the ceiling and the heat and before the Mac-wide cap. It never halts, it writes no waiting record (removing the caller's earlier one: it waits on its Login, never in the Mac's line), and idle-slots reads `hold-quota` (quota-bound). It is always the lead's own Login, never a reader's: `status` never reads it, and the lead's lease names its Login (`login`, written by every `next` off `--dry-run` and every `record-entry`), which the Watchdog's reading (`moving`, run in the Watchdog's or the Companion's own process) reads in place of its own while that lease holds; a lapsed, missing or loginless lease holds nothing, so a dead lead's held rows read as work and silence judges them (status SKILL.md § The Watchdog's reading).

**Full suites.** `verify-slot.py` takes a slot only while the slots held plus the slots it needs fit in min(N, C), C read per poll from a fresh reading (its raw `capacity`, which can only lower N); any read failure reads N. A C below the slots held blocks new acquirers and never stops a holder. **The Capacity stop** (p36-10, `verify-slot.py` contract 7) does: while a fresh reading's `signals.stop_suites` is JSON `true` (`capacity.py`'s `CAPACITY_STOP_KEY = "stop_suites"`), no verify slot is free (`verify-slot: waiting (memory: critical)`), and a running slotted suite is stopped through its guard and put back in line, to restart from the beginning once the flag clears and memory falls below warning, as the Heat hold's trapping stop restarts only below heavy (§ Heat). Its label is `memory: critical` when `signals.memory` is at least 4 (`CAPACITY_MEMORY_CRITICAL`), else `capacity: stop_suites`. **The restart hold** (p39-7): the run a Capacity stop put back in line also waits, at each poll the heat and the stop leave free, while a fresh reading's `signals.memory` is an integer (never a bool) of at least `CAPACITY_MEMORY_WARN` (2, warning): `verify-slot: waiting (memory: warning, after a capacity stop)` (`memory: critical, after a capacity stop` at 4 or more), and its no-verdict lines name that label. A fresh suite, and a run a heat stop put back in line, never wait on it. A restart-held run holds no place in line and no Integration waiter file, so it never holds back a fresh suite, and it registers again, at the back, at its first poll the hold leaves free. A missing, stale or unreadable reading, a `memory` that is null, a bool, a string or below 2, or a capacity.py with no `restart_hold` holds nothing. The heat is read first: at heavy or worse the heat holds the wait (`waiting (heat: …)`), and at trapping or worse a stop is a heat stop; at heavy, below trapping, a fresh `stop_suites` still stops a running suite, with a `capacity stop` line. A missing, stale or unreadable reading, or a capacity.py that will not load, stops nothing. Each capacity.json read and `suite_stop` call runs with TERM, INT and HUP held, so a stop that lands in it is delivered as it ends and never read as no reading.

**Interactive sessions are load.** Nothing gates them: what they cost reaches Chorus's signals, and so C.

**Mixed snapshots** (ADR 0043). An engine snapshot from before p36-7 reads no capacity.json and counts no Legs, so it stays at the Trickle, the more conservative; its claims write drops a Leg's waiting record (*A fair share*'s rule for a serial record), and the Leg's wait re-records within 10 minutes. An older Leg writes no lease, so it is uncounted. An older Run-record validator never meets `hold-quota` or a `by` cap: only a new `next` and `mark-started` write them.

## Heat

The **Heat hold** (estate ADR 0009 d5): while the Mac is hot, nothing new starts and no suite is added to it. The afternoon of 2026-10-21 showed why: heavy agent work on battery reached thermal emergency, and the kernel held the power budget at 1 to 3 % until a forced power-off.

**The reading.** `notifyutil -g com.apple.system.thermalpressurelevel` gives the Mac's thermal pressure: 0 nominal, 1 moderate, 2 heavy, 3 trapping, 4 sleeping (`pmset -g therm` reports nothing on Apple Silicon). One function reads it, `heat_level()` in `skills/execute/scripts/verify-slot.py`, fresh on every call and never cached; `next` loads it from there. It fails open, like an unusable verify-slots dir: no `notifyutil` (Linux, CI), a non-zero exit, a 2-second timeout or output it cannot parse reads 0, and so does a `verify-slot.py` that will not load (Windows). `THREAD_HEAT_LEVEL`, an integer from 0 to 4, pins the level: the test suites pin it at 0 (`tests/run.sh`, `tests/lib/rollout-fixtures.sh`, `tests/lib/merge-task-env.sh` and every suite that reaches a reading), so a hot Mac never flips an assertion. Any other value is ignored.

**The limit.** `next` reads the level once a call, right after the Away state, so a refused call reads neither. At heavy or worse `slotLimit` is 0, so no new start, seeded revise or head Solo task launches. It holds Away too: heat overnight is still heat. **A restart still waits on the ceiling alone**, as under the Trickle: it takes back a task every lead already counts. A running call is never stopped by `next`; its own suite is the verify slots' to hold or stop (below).

**The hold.** A row held for want of a Slot reads `heat: the Mac is hot (<name>)`, the level's name, unless this rollout's ceiling is full (`ceiling:` first). It replaces the `trickle:` and `away cap:` reasons while the Mac is hot, and since no Slot is found the last starts never read the row. A head Solo task the heat holds gets the `heat:` reason, and the rows below it still read `behind solo [[…]]`. A whole-rollout (bare) git-env hold, a main-red hold (`next`'s `mainRed`), a pause and a standing rollout `hold_until` hold their rows themselves, so none of them ever reads `heat:`. A git-env trip that holds the lane only (ADR 0046) holds no Slot, so the Heat hold reads the rows as usual.

**It never halts.** A row the heat holds could start once the Mac cools, so while any row reads `heat:` the rollout is neither `stuck` nor `awaiting-sign-off`: `halt` stays null and the lead waits (execute § 4.5 step 1.6), even with nothing of this rollout in flight. A seeded revise the lead holds for want of `slotLimit` while the Mac is hot is a Heat hold, the same wait (execute § 4.5 step 1.5).

**The output.** `next` adds one key after `lastStarts`, every other key unchanged: `heat`, `{level, name}`, at every level. The Run record's `idle-slots` event reads `hold-heat` whenever the call holds a row on `heat:`, ahead of `hold-trickle`, `hold-away-cap` and `hold-last-start`; its `free` stays the ceiling's.

**The verify slots** (`verify-slot.py` contract 7). At heavy no verify slot is free: a new suite waits, `verify-slot: waiting (heat: heavy)`. At trapping or sleeping the wrapper also stops the slotted suite it runs (the guard's TERM, 10 s, KILL), releases its slot and goes back in line, at the back, to restart from the beginning once the level is below heavy. A suite that had already finished keeps its own verdict. A heat stop is never red: an agent's `run` exits only with its last run's rc, or 76 (`verify-slot: no verdict: …`) when stopped while the Mac is hot; the lead's `lead-integrate.py verify` re-queues inside its `--slot-wait` and reads `heat` (exit 76) once that wait runs out, as `noslot` (75) does for a slot. Both are no verdict. A fresh capacity.json's `signals.stop_suites` holds and stops slotted suites the same way (§ Capacity, *Full suites*; its restart also waits for memory below warning), and its Run-record word is `heat` too.

**Agents' own Turns run on.** The Heat hold starts nothing new and adds no suite; it never stops a running task call, whose model Turns go on (only its suites wait or restart).

## Away

While Lachy is Away (a fresh file with `away: true`), the **Away cap** A bounds the Rollout tasks running across the whole Mac in the Trickle's place (ADR 0049, overturning Chorus ADR 0104 d3, which ran every Rollout to its own ceiling). It counts as the Trickle does (§ The Trickle): the same count elsewhere, `slotLimit` at `min(ceiling, max(0, A − the count elsewhere − the places kept))`, and a restart that waits on the ceiling alone. Each rollout's `parallel_ceiling` still bounds its own share: a rollout whose own ceiling binds first reads `ceiling:`, as by day. A hot Mac still holds every new start Away (§ Heat).

**The value.** A is a fresh file's `away_cap`, and A is C while Capacity is in force (§ Capacity). With the key absent the built-in is 4: twice the Mac's two Verify slots (`verify-slot.py --slots 2`), so two suites run and two queue, where on the night ADR 0049 records eight rollouts ran to their own ceilings at load 139 to 149. A fresh file with no `away_cap` and a `trickle` of 4 or more lifts the built-in to `trickle` + 1, so the Away cap is always above the Trickle, as Chorus keeps it. Chorus's own default is the same 4, so a hand-written file without the key behaves as the Stage's. A stale, unreadable or missing file reads not Away, so the Away cap never binds there (§ Reading it).

**A meant wait.** A row the Away cap holds reads `away cap: <running>/<A> tasks running on this Mac`, and it never halts: a rollout the Away cap alone holds is a meant wait, never Stalled (ADR 0048), even with nothing of it in flight. `halt` stays null, the lead's turn ends `waiting` with that reason (execute § 4.5 steps 1.5 and 1.6), and the Run record's `idle-slots` reads `hold-away-cap`, so the Watchdog verdict reads a wait on the Away cap. A fair share's `kept for` suffix (§ The Trickle, *The hold*) reads the same Away.

**A dead lead's notes hold room.** The count reads notes, never sessions, so a rollout whose lead died holds its Away-cap room until its lease lapses, the Watchdog recovers it (ADR 0048) or Lachy pauses it (the `paused:` stamp, § The Trickle); the Companion has no pause.

**Tuning.** `mark-started` records the cap in force at each Slot start, slot-taken's `cap`, `{away, n, file}`, in the Run record, read once per run and silently (`next` prints the WARN). A Reflection reads it against suite times, verify reds and load once the record carries them (p29-10), and tunes A like any knob (ADR 0032, 0049); Throughput is the Guardrail on how low it may go, since a night of many rollouts finishes later per rollout by design.

What is still running at the Morning finishes; nothing new starts above the Trickle until he is Away again (Chorus ADR 0104 d4). The Evening's switch gives more room (the Trickle to the Away cap); the Morning's may leave `slotsInUse` above `slotLimit`, and then nothing new starts until the count falls. While Away runs to the Morning, the last starts hold a start that would not finish by it (§ The last starts).

## The last starts

Toward the Morning a task starts only if its kind's usual length ends it by the Morning's hour; with no history for its kind, nothing starts in the last two hours. Running tasks finish (Chorus ADR 0104 d4). `next` holds the start; the lead never reads the file or the history.

**When they apply.** All three must hold:

- a fresh file reads `away: true`;
- its `until` is the Morning: read in local wall-clock time (the Mac's system time zone, as `morning` is), `until` falls on `morning`'s HH:MM to the minute;
- M, that `until` with its seconds cut, is after now and at most 24 h ahead (now < M <= now + 24 h).

M is the same instant, at the local offset (an `until` written as `2026-10-03T22:00:00Z` under Australia/Melbourne gives M `2026-10-04T09:00:00+11:00`), so a night across a daylight-saving change needs no wall-clock arithmetic. `until` must be the Morning because Chorus writes it as the latest end among what holds now (Chorus ADR 0104 § Built): the Morning's hour for the Evening and its 05:00 to 09:00 tail, the block's end for an Away block, Lunch's end for the Lunch restart. So the Evening, its tail, an Away block ending at the Morning and § Without a writer's hand-written file all apply.

Nothing applies, and nothing is recorded, for any of these:

- the Lunch restart, or a daytime Away block (an `until` of 13:00, 17:00 or 22:05);
- an Away block ending before the Morning, or spanning it (until 11:00) while he is still away;
- Away with `until` on the Morning but more than 24 h out (a weekend block until Monday's 09:00 before Sunday's, a hand-written file far ahead);
- the 05:00 to 09:00 press of *the Evening, now* (until tomorrow's 09:00) toward today's 09:00: it applies only from today's 09:00, once tomorrow's Morning is 24 h out;
- not Away: by day, or a missing, stale or unreadable file. The Trickle already bounds the Mac.

**A task's kind and its usual length** (Chorus ADR 0099 d2's reading of past journals):

- A task's kind is its note's `scope:` (lowercased), else `unscoped`.
- Its past runs are read per project, the rollout's first `projects:` link (case ignored), from the folded `call-journal` lines of every per-rollout `<rollout>.jsonl` in the Run record's events dir (never `reviews`, `tunings`, `reflections` or `grades`). A file counts only when its rollout note (this rollout's own, or one `next`'s walk of `--tasks-dir` finds, `Archive/Rollouts/` included) names the same first project.
- A call counts when its latest terminal line reads `status: completed` and `mode: task`, with an integer `durationMs` of at least 1 and an integer `startTime`; its end (`startTime` + `durationMs`) falls in the last 30 days; its file's `run-bound` line for that runId carries no `resumedFrom`; and its task's note is found (its kind is that note's). Each runId counts once.
- The usual length is the median of the kind's lengths, with at least 3 past runs. Fewer than 3 is no history.
- A rollout with no `projects:` reads no history. An events dir, file or line that cannot be read reads fewer runs, so the fallback holds more, never less.
- The history is read once per call, and only when a start reaches the check or a ran-past line is due.

**The rule.** A start is held when now + its usual length is past M, so a start that ends exactly at M starts. With no history its length is 2 h: it starts until exactly 2 h before M.

**What they hold.** A queued task's start and a head Solo task's lone start, checked only once a Slot is found: a row held for want of one keeps its `ceiling:` (or `away cap:`) reason, since the Away cap, never the Trickle, binds while Away. Restarts are exempt: a stalled `in_progress` task, a set-aside task handed back and a seeded revise each re-enter a task already begun, and running tasks finish. The hold reads, quote-free:

- with history: `last start: <kind> usually takes <N> min (median of <k> past runs), past the Morning at <HH:MM>`, N the median rounded up to a minute;
- with none: `last start: no history for <kind> (<k> past runs, 3 needed), none starts in the 2 h before the Morning at <HH:MM>`.

A held row is skipped, never a stop: the next best row may still fit, so a short kind starts below a long one. A head Solo task the last starts hold reads `last start:`, and the rows below it read `behind solo [[…]]`. A whole-rollout (bare) git-env hold, or a main-red hold (`next`'s `mainRed`, a RACE revert that did not land), replaces every hold, and a pause holds its rows itself, so none of them ever reads `last start:`. A git-env trip that holds the lane only (ADR 0046) holds no Slot, so the last starts read the rows as usual.

**It never halts.** While any row reads `last start:`, the rollout is neither `stuck` nor `awaiting-sign-off`: `halt` stays null and the lead waits (execute § 4.5 step 1.6). At the Morning the file reads not Away and the Trickle takes over. The Run record's `idle-slots` event reads `hold-last-start` whenever the call holds a row on `last start:` (after `hold-trickle`, which never co-occurs, and after `hold-away-cap`, which can: a call holding rows on both reads `hold-away-cap`).

**The output.** `next` adds one key after `trickle`, every other key unchanged: `lastStarts`, `{morning, kinds}`. `morning` is M as ISO 8601 with its local offset, or null when the last starts do not apply. `kinds` is `{<kind>: {usualMinutes, history}}` for each kind this call's start candidates read, sorted: `usualMinutes` the median rounded up to a minute, or null with no history, and `history` the kind's past runs. It is `{}` when they do not apply, or when no candidate reached the check. `status` (p28-7) reports the same `lastStarts`, read as `next` reads it and silently, with each queued row's `lastStart`: the reason `next` would hold it on once a Slot frees, null with unmet dependencies or under a pause, main red or a whole-rollout git-env hold (status SKILL.md § 2). It writes nothing, so it records no night line.

## The night record

Per night, the starts the last starts held and the tasks still running at the Morning are recorded in each rollout's own Run record (`<rollout>.jsonl`, `skills/_shared/scripts/run_record.py`), the Reflection's input (ADR 0032), so a Reflection can tune the two-hour fallback and the Trickle's number (Chorus ADR 0104's Consequences). `next` is the one writer: off `--dry-run`, once its refusals pass, after its `idle-slots` event, each line best-effort. It reads this rollout's record once per call, and writes each line once (a missing record is an empty one):

- `away-night` `{morning}`, no task: one per (rollout, M), on any call where the last starts apply. It is the night's denominator, nights with no hold included. A daytime Away block never writes one.
- `last-start-held` `{morning, scope, history, usualMinutes?}`: one per (task, M), for each row of the call's final holds that reads `last start:`. A whole-rollout git-env, main-red or pause hold writes none.
- `ran-past-morning` `{morning, slotTakenAt, scope, history, usualMinutes?}`: for every `away-night` marker in this record whose M is at or before now, one per (task, M) for each task whose Slot was open at M: its first `slot-taken` before M, and no `slot-freed` (or `carried` in this, its from-file) at or before M, by the record's pairing rules. `slotTakenAt` is that `slot-taken`'s ts.

The Slots are read from the record, never from notes, so a Morning the lead missed (down at 09:00), or a file gone stale after it, is still recorded at its next call, whatever the file then says. A dead lead's Slots count here: the record has no lease (§ The Trickle), so a Slot stays open in it until its pair is written; a night whose writer died before the Morning ran at Trickle 2 from then on, so a task the Trickle started that was still open at M ran past it too. `scope` is the task note's kind (`unscoped` with no note); `history` and `usualMinutes` are the kind's reading at the write (`usualMinutes` only with history), so a Reflection tells a fallback overrun from an underestimate.

`morning` and `slotTakenAt` are UTC `Z` stamps. A night is keyed by its `morning`: its record is the union of the three kinds sharing that `morning` across every `<rollout>.jsonl`. A rollout with no `next` call while Away to the Morning (every Slot busy all night with tasks begun by day) writes no marker, so that night has no record for it. Serial rollouts never run `next`, so they are outside the last starts, as they are outside the Trickle.

An unreadable record writes no night line, since its dedupe cannot be checked: while the last starts apply, `next` prints one `run_record: warning: night record not written: <why>` line on stderr; otherwise it is silent.

**Who reads it.** A Reflection (p28-7): `skills/reflect/scripts/score.py`'s `nights`, for the Mornings the scored rollout marked across every same-host record, and the weekly span's `nights` (`reflect.py`), over every record. Each night shows its held starts and its ran-past tasks, a ran-past task classed a fallback overrun, an underestimate or unchecked, with a suggested longer fallback or higher Trickle for Lachy to act on by hand; score.py's header is the one copy of that classification. `status` and `moving` never read it.

## Without a writer

With no file, every rollout on the Mac runs at a combined Trickle of 2, nights included. To run a night at the Away cap before a writer exists, write the file by hand, atomically:

```sh
mkdir -p ~/.config/thread && python3 - <<'PY'
import datetime, json, os
now = datetime.datetime.now().astimezone()
until = now.replace(hour=9, minute=0, second=0, microsecond=0)  # the next 09:00 strictly after now
if until <= now:
    until += datetime.timedelta(days=1)
until = until.replace(tzinfo=None).astimezone()  # that 09:00's own offset, a daylight-saving change overnight included
path = os.path.expanduser("~/.config/thread/away.json")
with open(path + ".tmp", "w") as f:
    json.dump({"away": True, "until": until.isoformat(), "morning": "09:00", "trickle": 2, "away_cap": 4,
               "written_at": now.isoformat()}, f)
os.replace(path + ".tmp", path)
PY
```

Its `until` is the Morning, so the last starts apply to it (§ The last starts). A hand-written file goes stale at its `until`, or 24 h after its `written_at`, whichever comes first; from then on each lead prints the `WARN: ~/.config/thread/away.json stale: …` line on every `next` call, and the Mac is back at Trickle 2. Delete the file to go back to the default with no WARN.
