# /thread:next — what's my next move?

The router for the undecided moment. A sibling of the decisive routes, not their parent (ADR 0002): when Lachy already knows what he wants, the decisive verb is faster and can't be second-guessed. `next` exists for "I don't know what to do with this thread" — it reads the situation, decides, and dispatches, asking only when the pick is his.

**Contains no route logic of its own.** Executing a chosen route means running that sibling's SKILL.md logic (`${CLAUDE_PLUGIN_ROOT}/skills/<route>/SKILL.md`), so every behaviour lives in exactly one place.

**Plugin root.** A command taken from text read as a file (a plugin file this skill sends you to, or this SKILL.md itself when a router or `sed` reads it instead of the Skill tool rendering it) runs by `${CLAUDE_PLUGIN_ROOT}/skills/_shared/plugin-root.md`.

## Process

1. **Read the situation**:
   - The live conversation — what's been done, what's mid-flight, what's blocked.
   - The active `THREAD.md`, if any (identify per `close`'s "Identify the active thread" chain).
   - Open vault tasks whose `projects:` match this project (`rg` across `~/repos/obsidian/Work/Tasks/`) — existing commitments shape the recommendation.
   - **Whether the work continues in another session** — it does when a handoff doc this session wrote now reads `status: consumed` in its front matter, or is gone because its consumer's close deleted it (this session did not withdraw it), or when another live session holds this thread: the Chorus Stage's session list shows it, or the handoff itself started the successor (the Chorus Stage, or the native task in Codex Desktop), whatever its doc still reads. Nothing else counts, so a doc still `pending` whose successor the handoff never started (a manual handoff whose prompt nobody has opened yet) does not. When there is a handoff doc, also note for the archive line's close part (step 4) whether its `**Run from:**` line is this checkout. A Rollout launch never counts (handoff **Rollout launch.**): a doc whose front matter carries `launches:`, and the lead it started, run a rollout, never this thread.
   - **After this session's own handoff** — when handoff § Next for this session runs this (its args `after-handoff <abs doc path>`), the work that doc hands off is its consumer's: it is never this session's keep-going step, and it is never handed off again. The bullet above still settles where the thread lives: when a successor the handoff started (a raised Chorus card, a created Codex Desktop task) holds the thread, step 3's **While another session holds the thread.** rule and step 4's archive line govern, residual work or not (with the process record unwritten, that move is close, step 3). Only a manual handoff, whose doc is still `pending` with no successor started, takes its move from what is left in this session: keep going on work the doc does not hand off, stash, or defer. With nothing left the move is close, and its pending doc owns the continuation (close § The handoff owns the continuation). When close would land this session's own branch, and the doc's `**Run from:**` line is this checkout, the close line adds ", which the fresh session will build on". After this session's own handoff, next prints no step-2 summary and no open question, because the handoff output already said where the work is: it prints only its one line, or the menu when the pick is his, with no question outside that menu (an open confirm step 3 settles or carries keeps its Answered line or its carrier, as steps 3 and 4 say).
   - **An open question this session left** — whether this session's last turn ended on a question Lachy has not answered: an AskUserQuestion still open or dismissed when `/thread:next` arrived, or a question closing the reply ("Write the regenerated rollout?", "Shall I carry on?"). `/thread:next` arriving answers nothing, so it is an **open confirm** that step 3 settles (by its Owner, `${CLAUDE_PLUGIN_ROOT}/skills/_shared/asking.md` § 1) before it recommends. A sweep (Lachy running `/thread:next` in several sessions in the same minute) is no answer to any of them either: each session settles its own.
   - **This session's process record** — read only when the work continues in another session (above), since only an archive loses it; this read writes nothing. The record is **unwritten** when either half holds, and step 4's line names the half: **no THREAD.md**, the conversation has thread shape (close § Identify the active thread, rung 4's test), that chain finds no THREAD.md on disk, because it stops at rung 4 or its rung 1 would create the file, and, when this session wrote a handoff doc, open § Repo-thread lookup run with `slug=` that doc's `thread:` (the slug this session wrote into it, which its own context still holds when the consumer's close has deleted the doc) prints nothing. The chain alone cannot settle it: its rung 2 reads only a slug named in the conversation or a doc this session picked up, never one it wrote, and the consumer's close may already have created the thread under that slug (`_shared/threads/<slug>.md` for a workspace seat). A hit there means this half does not hold, and step 5's close takes that file as the active thread; or **no METHOD.md capture**, the session has an observation that meets `${CLAUDE_PLUGIN_ROOT}/skills/_shared/process-scan.md` § The bar and no row of its own in the `## Candidates` of the METHOD.md that file's routing test resolves, a ledger not created yet included. Most sessions have none, and on Windows, where that scan NOOPs, this half never holds.
   - **A task a wait names, not started** — each task the work waits on, read exactly as close step 2's **Tasks a wait names.** reads it: its sources (the active THREAD.md's waits as they stood before this session's first write, a wait this session's own work names, a task it filed to unblock itself included, and each paused rollout this session leads or the active THREAD.md names), its one read-only `unfinished-rollout.py awaited` run (it writes nothing), and its holds. Only `unstarted <task> (<Project>)` with no hold counts: step 3 decides its start and step 5 runs it. A held task starts nothing, and step 4's line names it; any other line, or a failed check, leaves the task out. While another session holds the thread, only a wait this session's own work names is checked here.
   - **This session's own branch** — whether the checkout is on a branch close would land as this session's own (close § The own branch). Every close line, part or option names that landing (step 4): the move's line and the menu's as well as the archive line's. The close line for an unwritten process record names the branch as left to the other session instead, since that close does not land it (step 5).
   - **A rollout prepared, not started** — a parallel rollout note this session wrote, or one the active THREAD.md names (a **THREAD.md-named** note), that no lead runs yet. Check each read-only, exactly as close step 2's **Rollouts this session wrote.** checks it: its handover order, its guard for a THREAD.md-named note, whose (i) reads an earlier close's held step `/thread:execute [[<slug>]] (held: <why>)` for a hold that carries (his not yet, orient-all's `left[]`, a recorded handover) as that hold again, its `unstarted` call over the handoff scan's `# scanned` dirs (close § The handoff owns the continuation; the scan and `unstarted` write nothing), and its holds. Only `unstarted <slug> <root>` with no hold counts: step 3 decides its execute handoff and step 5 runs it. A held note launches nothing, and step 4's line names it; any other line, or a failed check, leaves the note out. While another session holds the thread, a note only THREAD.md names is not checked here.

2. **Summarise "where we are"** — a headline (1–2 sentences) plus the single most important open question. A carried open confirm (step 3) is that question. Written for Lachy catching up, not a log. None after this session's own handoff (step 1), whose output already said where the work is.

3. **Recommend ONE move**, with a one-line reason:
   - **Keep going** — name the next concrete step in *this* session. Right when energy + context are live and the step is clear.
   - **`defer [day]`** — the work should continue on a known day. Right when it's day-shaped ("tomorrow's problem").
   - **`stash`** — not the current focus, no known return date. Right when the honest answer is "not now, don't lose it".
   - **`handoff`** — the work continues *right now*, in a fresh session: the next phase is unrelated to this one, a spec is ready to execute, or the task deserves a fresh head. "New thread / new prompt" = this route.
   - **`close`** — the work is genuinely done for now; log this session into the thread's THREAD.md and commit. The THREAD.md's `state:` is unchanged (it stays active) unless Lachy says the thread is finished; with no THREAD.md, close saves the session's memory, knowledge and commits instead.
   - **Archive this session** — the work already continues in another session (step 1). Not a route: nothing is written (a launch or a start first, step 5's **A launch first.** and **A start, after the launches.**, is no part of this move), no sibling runs, the THREAD.md's `state:` stays active and the thread lives on in that session, and only Lachy archives this session (on the Chorus Stage, from its row). Recommend it whenever step 1 finds the work continuing elsewhere, unless this session's process record is unwritten (**An unwritten process record, close first.**).

   **Compact, within keep going.** In Claude Code, when the work continues in this session, the context is heavy (for example the statusline ctx % is high), the work sits at a phase boundary, and the history is still worth keeping, the keep-going recommendation adds compacting with a `/compact <focus>` line, which step 5 prints. Build `<focus>` from the thread's state: the active THREAD.md's scope and next step, else the conversation's goal, the next step and the files in play; one line, no shell quoting. `next` never runs `/compact` itself: it is a user-typed command that runs only between turns, so only Lachy can type it, and `next` never dispatches, schedules or simulates it. A **correction loop** (the same fix corrected twice or more) gets `/rewind` ("Summarize from here" over the failed span) or a fresh start instead, never compact, because compacting carries the failed attempts forward in the summary. An unrelated next phase, a spec ready to execute, or a task that needs a fresh head is the `handoff` route, not compact. `/compact` and `/rewind` are Claude Code commands, so a Codex session gets no compact or rewind line: where Claude Code would recommend compact or `/rewind`, a Codex session recommends a fresh start through `handoff`. Compact is a recommendation inside keep going, not a route: the step-4 menu gains no compact option.

   **A rollout prepared, not started, starts first.** A note step 1 found gets its execute handoff, decided and never asked (Owner *gate*: he scheduled the work to run, `${CLAUDE_PLUGIN_ROOT}/skills/_shared/asking.md` § 1; ADR 0057 d2, ADR 0072). The launch is no move of this session's: step 5 runs it first, then this session's own move, which is recommended here as if no rollout waited, in the same turn. The rollout is never this session's keep-going step, and its launch never makes the work continue elsewhere (step 1: a Rollout launch never counts). While another session holds the thread, a note this session wrote launches all the same, as a decided act whose inputs only this session holds, and the archive line follows it. A held note gets no launch: the line names it (step 4).

   **A task a wait names starts too.** A task step 1 found gets its start, decided and never asked (Owner *gate*: the work is technical and this thread already waits on it, `${CLAUDE_PLUGIN_ROOT}/skills/_shared/asking.md` § 1; ADR 0082). Like a prepared rollout's launch, the start is no move of this session's: step 5 runs it after any launch, then this session's own move, recommended as if nothing waited, in the same turn, and it never makes the work continue elsewhere. While another session holds the thread, a task this session's own work waits on starts all the same, and the archive line follows it. A held task gets no start: the line names it (step 4).

   **While another session holds the thread.** Keep going, handoff, stash and defer drop from the recommendation and the line: keep going and handoff would put two sessions on the same work and the same THREAD.md, and stash and defer would set its `state:` to parked or paused and file a capture for work that is live elsewhere. Close stays offered, as the archive line's close part, because it declares nothing false: it leaves `state:` unchanged (`handoff-lifecycle.md` § Thread state's close row) and prepends one session-log line. It still writes to what the other session holds, so Archive stays the recommendation: close step 4 rewrites the Resume instructions when the handoff doc they point at is consumed or missing, its close-out commit lands on the checkout's current branch, and sub-step 7.9 reviews this session's own branch and queues its merge, which the other session may still be building on (close § The own branch). The close part names that landing whenever close would run it (step 4). Only an unwritten process record outweighs them, and only for what a decided close still writes (the next paragraph): the THREAD.md and its METHOD.md row, with their close-out commits, since that close skips sub-step 7.9 and leaves this session's own branch to the other session.

   **An unwritten process record, close first.** When step 1 finds this session's process record unwritten, the move is `close`, not Archive: a handoff runs no process scan, so once Lachy archives this chat that record is gone (on 9 Nov 2026 `next` said archive after a handoff, on a project with no THREAD.md or METHOD.md, and Lachy caught it: "we'd be losing that information"). Close creates what is missing: the THREAD.md through close § Identify the active thread, the METHOD.md row through its category 7. Its sub-step 7.9 does not run: this session's own branch is left, neither reviewed nor queued, to the other session, which may still be building on it (step 5's **Close for an unwritten process record, dispatched.**). It is decided and never asked, as Archive is. The rest of **While another session holds the thread.** stands: keep going, handoff, stash and defer still drop, and close leaves the thread's `state:` unchanged.

   **An open confirm, settled first.** Before recommending, settle the open confirm step 1 found: it is never silently dropped. Label its Owner by `~/.agents/knowledge/how-lachy-decides.md` (Chorus ADR 0110); its four rows split two ways. **Decided by the rule:** a gate (a confirm before a write, a queue or plan he already approved, "shall I carry on?", "archive?", a review STOP), a technical question (mechanism, architecture, config, a file format: "SQLite or Postgres?"), researched first, unless the project's card names him as steering that detail, which makes it his, and a priorities question, one that file or the project's `## Priorities` card already answers. Decide it as that file says, act on the decision as this session would have on his answer, say so in one line of its own ("Answered: <the question>: <the decision>, because <the reason>.", that file's *Decided for you*), then recommend from the situation that leaves. **Carried:** his question (intent, how important, how robust, his taste or lived use), and any act the shared action policy (`~/.agents/skills/_adapter-common/action-policy.md`) reserves for his approval, which is never answered by the rule, whatever its wording: an outbound send (an email, a message, a post), publishing, spend beyond the standing approval, an irreversible, destructive or device act, or a gated input a rollout plan declares (ADR 0008). It is carried, word for word, in what the move leaves behind: keep going asks it again before the next step; stash and defer write it into the capture's resume prompt; handoff writes it into the handoff doc's § What remains as a fork returned to Lachy, so the paste-ready prompt's `Gates:` line carries it too; close into the THREAD.md's Resume instructions (with no THREAD.md, close's own report); archive writes nothing, so it takes the carrier below. The move's line (step 4) then ends "Carried: <the question>."

   **An open confirm, while another session holds the thread.** The archive move writes nothing, and once Lachy archives this chat whatever only it held is gone (Q54's lost rollout note), so a decided act or a carried question gets a real carrier, the first that fits. A decided act whose inputs only this session holds (a draft in its own context, a regenerated rollout note) is done here, in step 3, and its Answered line names what it wrote; the archive move itself still writes nothing. Else, on the Chorus Stage, relay the decision or the question, word for word, to the session that holds the thread (`relay_session`, which it takes at its next rest), and the archive line ends "Relayed to <the other session>: <the decision or the question>." Failing both (off the Stage, or the relay refused because that session waits on Lachy), the archive line ends plainly "Pass this on to <the other session> before you archive this chat, or it is lost: <the decision or the question>." When the move is `close` instead (**An unwritten process record, close first.**), close writes, so an open confirm takes **An open confirm, settled first.**'s carrier and this paragraph does not apply.

4. **Decide the move, and say so in one line.** "Next move?" is a gate, never Lachy's question (Chorus ADR 0110: the loop audit of 21–25 Oct found 13 of its 23 forced questions were this one or "archive?", and two of them each held a session 23 hours). When the recommendation is clear, take it with no AskUserQuestion: print one line, then go straight to step 5. The gate: `${CLAUDE_PLUGIN_ROOT}/skills/_shared/asking.md` § 1.
   - **Clear** — step 1 settles the move by itself: the work continues in another session (archive) or does so with this session's process record unwritten (close), the work is done with nothing mid-flight (close), the next step here is named and the context is live (keep going), a day is named or the work waits on a dated event (defer), the conversation set it aside with no day in sight (stash), or the next phase is unrelated or a spec is ready to execute (handoff). Most moments are clear.
   - **Not clear** — only when the pick turns on something only Lachy knows: whether the thread is finished, whether and when he will come back to it, or how much it matters to him now. Then the move is his question: ask it once, through the menu below.
   - **The line.** `Next move: <move>, because <reason>. <What it leaves behind, so he can overturn it>.` For example: "Next move: close, because the export work is merged and nothing is mid-flight. The thread stays active, logged with this session, and `/thread:open` picks it up again." It ends "Carried: <the question>." when step 3 carried an open confirm.
   - **The launch, first in the line.** After a launch (step 3), the line opens `Next move: hand [[<slug>]] to a fresh lead, then <move>, because its note is written and no lead runs it, and <reason>.` Then, before what the move leaves behind and before any `Carried:`, it adds `A fresh session runs /thread:execute [[<slug>]] from <root>; say "not yet" to withdraw the handoff.` Several notes are named together in the opening (`hand [[<slug>]] and [[<slug>]] to fresh leads`), with that sentence once for each. A held note (step 1) gets no opening of its own: the line opens as it would with no rollout and adds `[[<slug>]] is not started (<the hold>); say "hand it off" to start its lead, or run /thread:execute [[<slug>]] in <root>.` His "hand it off" to that held-note line runs `${CLAUDE_PLUGIN_ROOT}/skills/handoff/SKILL.md` through its **Rollout launch.** for that note (orient § 9's **Fresh session**), never a handoff of this thread. When the move is not clear there is no line: each launch's `A fresh session runs …` sentence, and each held note's sentence, prints on its own line just before the menu (the menu below), so his overturn still has its place.
   - **A started wait, in the line.** After a start (step 3), the line opens `Next move: start [[<task>]], then <move>, because <the work> waits on it and nothing builds it, and <reason>.`, or, after a launch, `Next move: hand [[<slug>]] to a fresh lead and start [[<task>]], then <move>, …`, and adds `/thread:schedule --tasks <task> takes it; say "not yet" to hold it.` before what the move leaves behind and before any `Carried:`. His "not yet" after the start undoes it the way it went: a new note's launch is withdrawn as a launch's is, and a join is deferred out of its rollout by `/thread:repair [[<rollout>]]` (its § 5); the wait then holds as his not yet (close step 2's holds). A held task adds `[[<task>]] is filed, not started (<the hold>); say "start it" to schedule it.`, ending at `(<the hold>).` for a note schedule step 1 never takes (`archived`, `not a task`, `a decisions task`: close step 2's item 2), and his "start it" runs `/thread:schedule --tasks <task>`, after lifting a paused rollout's held wait for it as close sub-step 7.11 lifts it. In the line and in every carrier the own move writes, a task is coming ("once [[<task>]] lands") only when step 1's read printed `scheduled` (not paused) or `building` for it, or step 5 starts it; otherwise it is `[[<task>]] is filed, not started` (ADR 0082 d5). When the move is not clear these sentences print on their own line just before the menu, and the archive line takes them where it takes a launch's.

   **The menu, when the move is not clear.** Offer the routes via `AskUserQuestion`, in `${CLAUDE_PLUGIN_ROOT}/skills/_shared/asking.md`'s Framing: recommended option first with "(Recommended)", the other viable routes after (drop any that plainly don't apply; keep ≤4). Option descriptions say what each route would *do to this specific thread* ("task on tomorrow's page", "committed handoff doc + prompt to paste into a fresh session"), not generic definitions.

   **Session and thread, in the line and the menu.** In wording Lachy reads (the line, option labels and descriptions) say **session** for this chat and **thread** for the durable work its THREAD.md records, the user-facing convention in CONTEXT.md's **Thread** entry; agent-facing prose, this file's included, keeps that entry's two senses. Never offer a bare "Leave it" or "Keep thread", which leave him guessing what happens to the session and to the THREAD.md. Every close line, part or option says what close writes: the log into the thread, which stays active (with no THREAD.md, what close saves instead), and this session's own branch when close would land it.

   **The archive line.** After a launch (step 3), the launch's own `A fresh session runs /thread:execute [[<slug>]] from <root>; …` sentence (**The launch, first in the line.**) opens the line, before its two parts, and the archive part's "Nothing is written." reads "Nothing else is written.", since the launch wrote and landed its doc. After a start (step 3) it reads "Nothing else is written." too, since its schedule wrote. A held note's sentence (**The launch, first in the line.**) opens the line the same way, after any launch's, and changes nothing the parts say. When step 1 finds the work continuing in another session, with the process record written (else the close line below), archiving is always clear ("archive?" is a gate), so there is no menu: the line is exactly two parts, after the launch's sentence when there was a launch, in this order, then, when step 3 relayed an open confirm or left it to Lachy to pass on, its carrier's closing sentence ("Relayed to …" or "Pass this on to …"). A bare "Carried: <the question>." never ends this line, since nothing the archive move writes would carry it:
   - the archive part, "Next move: archive this session. Nothing is written. The thread stays active in <the other session>; archive this chat on the Stage, from its row." After a launch, "Nothing else is written." stands in for "Nothing is written.". Off the Stage the last clause names the host's own act: "archive this task in the sidebar" in Codex Desktop, "end this session" elsewhere. When the other session has itself closed, name where the thread was last logged instead of a live session.
   - the close part, "Say close instead to log this session into the thread (it stays active)." When close would land this session's own branch `<B>` (step 1), add "Close also reviews `<B>` and queues its merge", plus ", which <the other session> is building on" when the doc's `**Run from:**` line is this checkout. With no THREAD.md, the part names what close saves instead (memory, knowledge, commits).

   **The close line, when the process record is unwritten.** Step 3's close first is clear too, so there is no menu: one line in **The line.**'s form, a launch's or held note's sentence where **The launch, first in the line.** puts it. `Next move: close, because the work continues in <the other session> but <what is unwritten> would be lost with this chat. <What close writes>. The thread stays active in <the other session>; once close's report prints, archive this chat on the Stage, from its row.` Close runs at once (step 5), so the line offers no overturn: what it leaves behind is where the thread lives on and when to archive this chat. Off the Stage the last clause names the host's own act, as the archive part's does: "archive this task in the sidebar" in Codex Desktop, "end this session" elsewhere. When the other session has itself closed, name where the thread was last logged instead of a live session. <What is unwritten> names the half or halves step 1 found ("no THREAD.md records this session", "its process observations are in no METHOD.md"). <What close writes> names what it creates, then the log into the thread, and, when close would otherwise land this session's own branch `<B>` (step 1), says `<B>` is left to <the other session>, neither reviewed nor queued (step 5).

5. **Dispatch.** Run the decided (or picked) move's sibling logic in full — task-writer capture for stash/defer, the committed `docs/handoffs/` doc + paste-ready prompt for handoff (plus the native task in Codex Desktop or a Chorus Session), with handoff § Next for this session skipped (this step already decided this session's move), the complete persist-and-commit ritual for close. "Keep going" means exactly that: state the next step and continue working, no ceremony. When compact was recommended, print the `/compact <focus>` line once, for Lachy to type, and end the turn, never run it: `/compact` runs only between turns, so working on would keep filling the context it relieves. The focus already names the next step, so work resumes after Lachy compacts.

   **A launch first.** For each note step 1 found (step 3), in the order it found them, run `${CLAUDE_PLUGIN_ROOT}/skills/handoff/SKILL.md` through its **Rollout launch.**, with orient § 9's **Fresh session** continuation: start in its Project root `<root>`, then `/thread:execute [[<slug>]]`. The launch is a dispatch, so handoff § Next for this session is skipped for the launch. Its output never ends the turn: `next` then dispatches this session's own move, decided in step 3 as if no rollout waited, in the same turn. With close as the move, close step 2 reads the launch as a handover, so close launches nothing more and its step 4 logs `handed [[<slug>]] to a fresh lead`. Each carrier the own move writes (a capture's resume prompt, the thread handoff doc's § What remains, THREAD.md) names the rollout as handed to a fresh lead, never as a `/thread:execute` step left to do. When the move is not clear, the launch runs before the menu is asked, and its sentence (step 4's **The launch, first in the line.**) prints on its own line just before the menu.

   **A start, after the launches.** For each task step 1 found (step 3), in its order, after every launch: run `${CLAUDE_PLUGIN_ROOT}/skills/schedule/SKILL.md` with `--tasks <task>`, exactly as close sub-step 7.11 runs it (a join of its project's running rollout, ranked first, or a one-task note handed to a fresh lead), its step 8 summary not printed, since the line says it. Its output never ends the turn: `next` then dispatches this session's own move. With close as the move, close step 2 reads the task as started by this transcript, so close starts nothing more and its step 4 writes the wait as coming. Each carrier the own move writes names the task as started, never as a wait nobody builds. When the move is not clear, the start runs before the menu is asked.

   **Archive this session, dispatched.** Apart from **A launch first.** and **A start, after the launches.**, which run before it and are no part of this move, write nothing and run no sibling: the archive line (step 4) already says where the work now continues (the other session, by its name), that the thread stays active there, and that Lachy can archive this session (on the Chorus Stage, from its row; elsewhere by the host's own act), so print it and end the turn. `next` never archives a session itself: only Lachy does.

   **Close for an unwritten process record, dispatched.** Close's own logic in full, with three things settled by the line (step 4), which told him what close creates and what it leaves to the other session. The active thread: when step 1's lookup by this session's handoff doc's `thread:` found a file, close takes that file, as its rung 2 takes a picked-up doc's; otherwise the offer at close § Identify the active thread, rung 4 is already made, so close creates the THREAD.md by open § Creating a new thread, and asks neither for the offer nor for its slug and scope. When this session wrote a handoff doc, that slug is the doc's `thread:` value, since the consumer's close looks the thread up by it (close's rung 2; a doc written with no active thread carries its own handoff slug, `handoff-lifecycle.md` § Front matter), so both sessions write one thread, never two; with no doc it is taken from the conversation, and the one-line scope always is. Sub-step 7.9 (Land the own branch) does not run, as under `/thread:open save` and a Leg: the other session may still be building on `<B>`, in this very working tree when the doc's `**Run from:**` line is this checkout, so a push, a fresh review's fix commits and a queued merge would sweep in its in-flight work, and writing the process record needs only the THREAD.md and the METHOD.md row. Close's **Wrong route?** sends it nowhere: the work has already moved, and recording it is what this close is for. Close step 2 checks only this session's own work, as step 1 does while another session holds the thread: **Rollouts this session wrote.** checks no note only THREAD.md names, and **Tasks a wait names.** reads only a wait this session's own work names, since the thread's waits and its paused rollouts are that session's to start.

## Don't

- Don't recommend more than one move. The whole point is answering the question, not restating the options.
- Don't pad the summary — headline + top open question (none after this session's own handoff, step 2), then the line (or, when the move is not clear, the menu).
- Don't re-implement any route inline. Dispatch means running the sibling skill's logic as written.
- Don't run `/compact`, `/rewind` or `/clear` yourself, don't keep working after printing a `/compact` line, and don't offer compact as a route.
- Don't invoke this router when the user was already decisive — "stash this" is `thread:stash`, not a `next` conversation.
- Don't ask "next move?" or "archive?" when the recommendation is clear: decide it and say so in one line (step 4). The menu is only for a pick that turns on what only Lachy knows.
- Don't drop an open confirm, whether `next` runs alone or in a sweep: decide a gate, a technical or a priorities question by the rule, carry his question and any act the action policy reserves for him into what the move leaves behind, and give it a real carrier when the move is archive (step 3). - Don't label an option "Leave it" or "Keep thread", and don't say "thread" for this chat in the line or the menu: name the session and the thread apart (step 4).
- Don't recommend or offer keep going, handoff, stash or defer while another session holds the thread, and don't archive a session yourself: only Lachy does.
- Don't recommend archive while this session's process record is unwritten (step 1): close creates it, and archiving this chat loses it (step 3).
- Don't end a session with a rollout note waiting and no lead (step 1): its launch runs first, whatever this session's move, and is never put to him as a question; only his "not yet" or a hold (close step 2) stops it.
- Don't end a session with a wait on a task nothing builds (step 1): its start runs first, whatever this session's move, and is never put to him as a question; only his "not yet" or a hold stops it, and no line says a task is coming unless something builds it.
