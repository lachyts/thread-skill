# /thread:next — what's my next move?

The router for the undecided moment. A sibling of the decisive routes, not their parent (ADR 0002): when Lachy already knows what he wants, the decisive verb is faster and can't be second-guessed. `next` exists for "I don't know what to do with this thread" — it reads the situation, decides, and dispatches, asking only when the pick is his.

**Contains no route logic of its own.** Executing a chosen route means running that sibling's SKILL.md logic (`${CLAUDE_PLUGIN_ROOT}/skills/<route>/SKILL.md`), so every behaviour lives in exactly one place.

**Plugin root.** A command taken from text read as a file (a plugin file this skill sends you to, or this SKILL.md itself when a router or `sed` reads it instead of the Skill tool rendering it) runs by `${CLAUDE_PLUGIN_ROOT}/skills/_shared/plugin-root.md`.

## Process

1. **Read the situation**:
   - The live conversation — what's been done, what's mid-flight, what's blocked.
   - The active `THREAD.md`, if any (identify per `close`'s "Identify the active thread" chain).
   - Open vault tasks whose `projects:` match this project (`rg` across `~/repos/obsidian/Work/Tasks/`) — existing commitments shape the recommendation.
   - **Whether the work continues in another session** — it does when a handoff doc this session wrote now reads `status: consumed` in its front matter, or is gone because its consumer's close deleted it (this session did not withdraw it), or when another live session holds this thread: the Chorus Stage's session list shows it, or the handoff itself started the successor (the Chorus Stage, or the native task in Codex Desktop), whatever its doc still reads. Nothing else counts, so a doc still `pending` whose successor the handoff never started (a manual handoff whose prompt nobody has opened yet) does not. When there is a handoff doc, also note for the archive line's close part (step 4) whether its `**Run from:**` line is this checkout. A Rollout launch never counts (handoff **Rollout launch.**): a doc whose front matter carries `launches:`, and the lead it started, run a rollout, never this thread.
   - **An open question this session left** — whether this session's last turn ended on a question Lachy has not answered: an AskUserQuestion still open or dismissed when `/thread:next` arrived, or a question closing the reply ("Write the regenerated rollout?", "Shall I carry on?"). `/thread:next` arriving answers nothing, so it is an **open confirm** that step 3 settles (by its Owner, `${CLAUDE_PLUGIN_ROOT}/skills/_shared/asking.md` § 1) before it recommends. A sweep (Lachy running `/thread:next` in several sessions in the same minute) is no answer to any of them either: each session settles its own.
   - **This session's own branch** — whether the checkout is on a branch close would land as this session's own (close § The own branch). Every close line, part or option names that landing (step 4): the move's line and the menu's as well as the archive line's.

2. **Summarise "where we are"** — a headline (1–2 sentences) plus the single most important open question. A carried open confirm (step 3) is that question. Written for Lachy catching up, not a log.

3. **Recommend ONE move**, with a one-line reason:
   - **Keep going** — name the next concrete step in *this* session. Right when energy + context are live and the step is clear.
   - **`defer [day]`** — the work should continue on a known day. Right when it's day-shaped ("tomorrow's problem").
   - **`stash`** — not the current focus, no known return date. Right when the honest answer is "not now, don't lose it".
   - **`handoff`** — the work continues *right now*, in a fresh session: the next phase is unrelated to this one, a spec is ready to execute, or the task deserves a fresh head. "New thread / new prompt" = this route.
   - **`close`** — the work is genuinely done for now; log this session into the thread's THREAD.md and commit. The THREAD.md's `state:` is unchanged (it stays active) unless Lachy says the thread is finished; with no THREAD.md, close saves the session's memory, knowledge and commits instead.
   - **Archive this session** — the work already continues in another session (step 1). Not a route: nothing is written, no sibling runs, the THREAD.md's `state:` stays active and the thread lives on in that session, and only Lachy archives this session (on the Chorus Stage, from its row). Recommend it whenever step 1 finds the work continuing elsewhere.

   **Compact, within keep going.** In Claude Code, when the work continues in this session, the context is heavy (for example the statusline ctx % is high), the work sits at a phase boundary, and the history is still worth keeping, the keep-going recommendation adds compacting with a `/compact <focus>` line, which step 5 prints. Build `<focus>` from the thread's state: the active THREAD.md's scope and next step, else the conversation's goal, the next step and the files in play; one line, no shell quoting. `next` never runs `/compact` itself: it is a user-typed command that runs only between turns, so only Lachy can type it, and `next` never dispatches, schedules or simulates it. A **correction loop** (the same fix corrected twice or more) gets `/rewind` ("Summarize from here" over the failed span) or a fresh start instead, never compact, because compacting carries the failed attempts forward in the summary. An unrelated next phase, a spec ready to execute, or a task that needs a fresh head is the `handoff` route, not compact. `/compact` and `/rewind` are Claude Code commands, so a Codex session gets no compact or rewind line: where Claude Code would recommend compact or `/rewind`, a Codex session recommends a fresh start through `handoff`. Compact is a recommendation inside keep going, not a route: the step-4 menu gains no compact option.

   **While another session holds the thread.** Keep going, handoff, stash and defer drop from the recommendation and the line: keep going and handoff would put two sessions on the same work and the same THREAD.md, and stash and defer would set its `state:` to parked or paused and file a capture for work that is live elsewhere. Close stays offered, as the archive line's close part, because it declares nothing false: it leaves `state:` unchanged (`handoff-lifecycle.md` § Thread state's close row) and prepends one session-log line. It still writes to what the other session holds, so Archive stays the recommendation: close step 4 rewrites the Resume instructions when the handoff doc they point at is consumed or missing, its close-out commit lands on the checkout's current branch, and sub-step 7.9 reviews this session's own branch and queues its merge, which the other session may still be building on (close § The own branch). The close part names that landing whenever close would run it (step 4).

   **An open confirm, settled first.** Before recommending, settle the open confirm step 1 found: it is never silently dropped. Label its Owner by `~/.agents/knowledge/how-lachy-decides.md` (Chorus ADR 0110); its four rows split two ways. **Decided by the rule:** a gate (a confirm before a write, a queue or plan he already approved, "shall I carry on?", "archive?", a review STOP), a technical question (mechanism, architecture, config, a file format: "SQLite or Postgres?"), researched first, unless the project's card names him as steering that detail, which makes it his, and a priorities question, one that file or the project's `## Priorities` card already answers. Decide it as that file says, act on the decision as this session would have on his answer, say so in one line of its own ("Answered: <the question>: <the decision>, because <the reason>.", that file's *Decided for you*), then recommend from the situation that leaves. **Carried:** his question (intent, how important, how robust, his taste or lived use), and any act the shared action policy (`~/.agents/skills/_adapter-common/action-policy.md`) reserves for his approval, which is never answered by the rule, whatever its wording: an outbound send (an email, a message, a post), publishing, spend beyond the standing approval, an irreversible, destructive or device act, or a gated input a rollout plan declares (ADR 0008). It is carried, word for word, in what the move leaves behind: keep going asks it again before the next step; stash and defer write it into the capture's resume prompt; handoff writes it into the handoff doc's § What remains as a fork returned to Lachy, so the paste-ready prompt's `Gates:` line carries it too; close into the THREAD.md's Resume instructions (with no THREAD.md, close's own report); archive writes nothing, so it takes the carrier below. The move's line (step 4) then ends "Carried: <the question>."

   **An open confirm, while another session holds the thread.** The archive move writes nothing, and once Lachy archives this chat whatever only it held is gone (Q54's lost rollout note), so a decided act or a carried question gets a real carrier, the first that fits. A decided act whose inputs only this session holds (a draft in its own context, a regenerated rollout note) is done here, in step 3, and its Answered line names what it wrote; the archive move itself still writes nothing. Else, on the Chorus Stage, relay the decision or the question, word for word, to the session that holds the thread (`relay_session`, which it takes at its next rest), and the archive line ends "Relayed to <the other session>: <the decision or the question>." Failing both (off the Stage, or the relay refused because that session waits on Lachy), the archive line ends plainly "Pass this on to <the other session> before you archive this chat, or it is lost: <the decision or the question>."

4. **Decide the move, and say so in one line.** "Next move?" is a gate, never Lachy's question (Chorus ADR 0110: the loop audit of 21–25 Oct found 13 of its 23 forced questions were this one or "archive?", and two of them each held a session 23 hours). When the recommendation is clear, take it with no AskUserQuestion: print one line, then go straight to step 5. The gate: `${CLAUDE_PLUGIN_ROOT}/skills/_shared/asking.md` § 1.
   - **Clear** — step 1 settles the move by itself: the work continues in another session (archive), the work is done with nothing mid-flight (close), the next step here is named and the context is live (keep going), a day is named or the work waits on a dated event (defer), the conversation set it aside with no day in sight (stash), or the next phase is unrelated or a spec is ready to execute (handoff). Most moments are clear.
   - **Not clear** — only when the pick turns on something only Lachy knows: whether the thread is finished, whether and when he will come back to it, or how much it matters to him now. Then the move is his question: ask it once, through the menu below.
   - **The line.** `Next move: <move>, because <reason>. <What it leaves behind, so he can overturn it>.` For example: "Next move: close, because the export work is merged and nothing is mid-flight. The thread stays active, logged with this session, and `/thread:open` picks it up again." It ends "Carried: <the question>." when step 3 carried an open confirm.

   **The menu, when the move is not clear.** Offer the routes via `AskUserQuestion`, in `${CLAUDE_PLUGIN_ROOT}/skills/_shared/asking.md`'s Framing: recommended option first with "(Recommended)", the other viable routes after (drop any that plainly don't apply; keep ≤4). Option descriptions say what each route would *do to this specific thread* ("task on tomorrow's page", "committed handoff doc + prompt to paste into a fresh session"), not generic definitions.

   **Session and thread, in the line and the menu.** In wording Lachy reads (the line, option labels and descriptions) say **session** for this chat and **thread** for the durable work its THREAD.md records, the user-facing convention in CONTEXT.md's **Thread** entry; agent-facing prose, this file's included, keeps that entry's two senses. Never offer a bare "Leave it" or "Keep thread", which leave him guessing what happens to the session and to the THREAD.md. Every close line, part or option says what close writes: the log into the thread, which stays active (with no THREAD.md, what close saves instead), and this session's own branch when close would land it.

   **The archive line.** When step 1 finds the work continuing in another session, archiving is always clear ("archive?" is a gate), so there is no menu: the line is exactly two parts, in this order, then, when step 3 relayed an open confirm or left it to Lachy to pass on, its carrier's closing sentence ("Relayed to …" or "Pass this on to …"). A bare "Carried: <the question>." never ends this line, since nothing the archive move writes would carry it:
   - the archive part, "Next move: archive this session. Nothing is written. The thread stays active in <the other session>; archive this chat on the Stage, from its row." Off the Stage the last clause names the host's own act: "archive this task in the sidebar" in Codex Desktop, "end this session" elsewhere. When the other session has itself closed, name where the thread was last logged instead of a live session.
   - the close part, "Say close instead to log this session into the thread (it stays active)." When close would land this session's own branch `<B>` (step 1), add "Close also reviews `<B>` and queues its merge", plus ", which <the other session> is building on" when the doc's `**Run from:**` line is this checkout. With no THREAD.md, the part names what close saves instead (memory, knowledge, commits).

5. **Dispatch.** Run the decided (or picked) move's sibling logic in full — task-writer capture for stash/defer, the committed `docs/handoffs/` doc + paste-ready prompt for handoff (plus the native task in Codex Desktop or a Chorus Session), the complete persist-and-commit ritual for close. "Keep going" means exactly that: state the next step and continue working, no ceremony. When compact was recommended, print the `/compact <focus>` line once, for Lachy to type, and end the turn, never run it: `/compact` runs only between turns, so working on would keep filling the context it relieves. The focus already names the next step, so work resumes after Lachy compacts.

   **Archive this session, dispatched.** Write nothing and run no sibling: the archive line (step 4) already says where the work now continues (the other session, by its name), that the thread stays active there, and that Lachy can archive this session (on the Chorus Stage, from its row; elsewhere by the host's own act), so print it and end the turn. `next` never archives a session itself: only Lachy does.

## Don't

- Don't recommend more than one move. The whole point is answering the question, not restating the options.
- Don't pad the summary — headline + top open question, then the line (or, when the move is not clear, the menu).
- Don't re-implement any route inline. Dispatch means running the sibling skill's logic as written.
- Don't run `/compact`, `/rewind` or `/clear` yourself, don't keep working after printing a `/compact` line, and don't offer compact as a route.
- Don't invoke this router when the user was already decisive — "stash this" is `thread:stash`, not a `next` conversation.
- Don't ask "next move?" or "archive?" when the recommendation is clear: decide it and say so in one line (step 4). The menu is only for a pick that turns on what only Lachy knows.
- Don't drop an open confirm, whether `next` runs alone or in a sweep: decide a gate, a technical or a priorities question by the rule, carry his question and any act the action policy reserves for him into what the move leaves behind, and give it a real carrier when the move is archive (step 3). Never answer a send, a publish, spend beyond the standing approval or an irreversible act by the rule.
- Don't label an option "Leave it" or "Keep thread", and don't say "thread" for this chat in the line or the menu: name the session and the thread apart (step 4).
- Don't recommend or offer keep going, handoff, stash or defer while another session holds the thread, and don't archive a session yourself: only Lachy does.
