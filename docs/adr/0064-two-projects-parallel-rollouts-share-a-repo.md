# 0064 — Two projects' parallel rollouts share a repo

Date: 2026-11-02
Status: accepted. Ruled with Lachy in the 2026-10-30 grill behind `thread-skill-p33-4-parallel-rollouts-share-a-repo` (Phase 33 · Task 4): two projects' parallel rollouts may run in the same repo at once, each in its own copy, landing through the same merge queue one at a time and re-checked against each other. The technical calls below were decided for him in that task's approved plan. Amends ADR 0030 (decision 3), ADR 0042, ADR 0044 (deferred) and ADR 0060 (decision 5).

## Context

`~/repos/workspaces` carries code for many projects (Obsidian Vault, Health, Contacts admin, Research System). Until now a repo held at most one unfinished parallel rollout, whatever its project (ADR 0027, ADR 0030), so `obsidian-vault-rollout-2026-10-29` alone held the repo until it landed, and every other project's workspaces code queued behind it. ADR 0060 freed the serial chains a stuck rollout waits beside, and named this change as the one that would let two projects' parallel rollouts share a repo. Lachy:

> I want to be working with Rollouts more and more. Is there a way that we can be designing this so that we can have the different projects running side by side? Is there a switch in the system to be able to fix this in a more solid way.

Two rollouts in one rollout clone (ADR 0042) would share its worktrees, its canary windows and its default branch, so each project needs a clone of its own. Two rollouts landing on one origin would each integrate against a `main` the other moves, so their Integrations must still go one at a time, each re-verified on the `main` the other just moved.

## Decision

1. **One clone per (repo, project), named `<toplevel>-<slug>-rollout`.** The default clone keeps its name, `<toplevel>-rollout`; a second project's is `<toplevel>-<project-slug>-rollout`. The name ends in `-rollout`, so every clone prefilter keeps working, and `self-rollout-check.sh --in-place` finds its twin by a walk over names beside it: `<S>` first (the rule before this ADR), then `<S>` with trailing `-<part>` segments dropped one at a time, every later name that ends in `-rollout` skipped (another clone, never a twin), to the first main checkout of the same GitHub `<owner>/<name>`. open's `rc` is its shell port. `--resolve` and `--ensure` take an optional slug (`[a-z0-9][a-z0-9-]*`, never `rollout`, never ending in `-rollout`). In slug mode they refuse (exit 3) when `<toplevel>-<slug>` is a checkout of any origin, or none, since the clone's name is that checkout's own clone's; and when the walk from the clone's name would land on another same-origin checkout. Either refusal says the project takes no clone of its own and waits for `<toplevel>-rollout`.

2. **Schedule § 0 asks which clone first.** § 0's project is the project whose `Local:` line it reads (`--project`, the orient-all fork's `projectSlug`, or a standalone `--tasks` run's first project with a `Local:` line). `unfinished-rollout.py clone --repo <Local:> --project <name>` prints `default`, `project <slug>` or `refuse <slugs>`. Its rules, in order: reuse the clone this project's own unfinished rollout runs from (by its recorded Project root, never a recomputed name, so a renamed project keeps its clone); else the default clone unless another project's rollout holds it; else this project's own, when its slug can name one, no other project's rollout holds it and it collides with no checkout (one read-only `--resolve` probe; it need not exist); else refuse, naming each taker. A legacy rollout rooted in place at the toplevel holds every clone. The `# thread:self-rollout-check` snippet carries the slug as `S`.

3. **The check counts per repo and project.** `unfinished-rollout.py check` (step 2c) refuses another project's unfinished rollout that shares this run's checkout (its clone, or that clone's in-place twin), and drops one in its own clone with a WARN: both run. Rules 3-5 then read one unfinished rollout per repo and project, and the supersede stays per project. A `--tasks` run whose tasks share no project keeps the old one-per-repo rule.

4. **A resume meets another project's rollout in its own clone.** `check --resume`, parallel shape, refuses a resuming rollout when another project's rollout that has run holds its clone and began earlier (its Run record's first line; ties and unreadable records by slug). Execute's *Surface re-check* halts it, and `--regenerate` moves it to its own clone. That settles two manual schedules that raced to one clone.

5. **The origin lane: Integration stays serial per origin across rollouts, passed in turn.** `mark-integrating`, under a machine-wide lock, takes a rollout's lane only while no other rollout on the origin holds its own: a root-level, open, parallel rollout note on the same origin, whatever its `engine_snapshot:`, with no `paused:` stamp, a fresh lease, a readable Run record whose lane is open on a task with no merge hold and no open halt, and that task's note holding the lane. Lapsed, none, unreadable and room-stop leases never hold, nor does an unreadable record, and a merge hold frees the origin lane. It also yields to the rollout that has waited longest: a refused caller is recorded on `origin-lane.json`'s waiting list (its `since` kept across refusals; an entry lives 30 minutes, and a waiter counts only while its lease is fresh, its record has no open halt, it is not paused and its task still awaits Integration). Ties break by rollout stem. A refusal exits 4 with an `ORIGIN LANE:` line, writes no note and frees the caller's own Run-record lane (`lane-freed release=origin origin=<owner/name>`). No caller is exempt, a Base-moved re-run included. Every unreadable thing fails open to today's behaviour, and the correctness invariant stays merge-task's base pin: it merges only onto the base its Integration used, and its exit 3 re-integrates. The origin lane saves wasted verifies on a stale `main`, keeps cross-rollout contention off the base-moved cap, and keeps two merge-tasks out of the seconds-wide RACE window.

   *Older Engine snapshots.* A rollout on a snapshot older than this ADR runs its own `mark-integrating`, which has no origin lane: it never checks, waits or writes an entry. From p28-4 on, its engine writes a lease and `lane-taken`, so while it integrates it reads as a holder to a newer rollout, which waits. It never waits for the newer one, so the two can integrate at once, and the base pin keeps every merge correct. An engine older than leases leaves lease state `none` and never holds.

6. **Execute's Origin lane wait.** Exit 4 at any of step 3's three `mark-integrating` sites (step 3's start, `prepare` exit 1's run, step 4's Base-moved re-run) is never a refusal, a set-aside or a halt: the lead prints the line, treats its lane as free, launches nothing more for that task, and launches the **origin wait** (`reconcile-rollout.py origin-wait`, read-only, every 20 s the grant rule, at most 900 s) in the background (in Codex, the foreground). Its return re-enters step 1; step 1 still fills slots, step 1.4 takes no task into step 3 again that turn, and step 1.6 ends it `waiting` with `reason="origin lane: waiting on <owner/name> behind [[<rollout>]]"`. The heartbeat is the fallback for a lost notification. The origin wait holds nothing: heartbeat clause (4) never waits on it, and a room stop or a hard pause never stops it.

7. **The Mac-wide cap is unchanged.** The Trickle and the Away cap (ADR 0049) already count every rollout's running tasks; nothing here raises them.

8. **The estate pass resolves each project's clone.** estate-scan runs `clone` per declaring project, then that project's own `--resolve`, root facts and unfinished-rollout check, and reports each in the repo row's `projects[]`; the row keeps the default resolution and carries no project's unfinished-rollout refusal. estate-rank reads a run's root and blockers from its home project's entry, and keys `sameRoot` on `rolloutRoot`. estate-dispatch's root contest is per project, and two parallel entries on one origin never share a batch (each fork's § 0 `clone` reads clones the other has not yet taken).

9. **Supersede, status, repair and reflect read each rollout separately.** The Reflection's Escapes sweep groups a repo's Project roots by family (a root's in-place twin), so two projects' clones of one checkout raise no flag. Its knob rule stays per repo on purpose: `rollouts.toml`'s knobs are one table per origin, shared by both projects, so landing from two rollouts' proposals in one Reflection could move one key both ways; every proposer is recorded, and the older rollout's proposal counts toward agreement at the next Reflection.

10. **Branch collisions.** Two projects' rollouts share the engine's branch namespace, `audit-fix/<slug less its first segment>`. Schedule step 5's Branch check (`unfinished-rollout.py branches`) leaves a task out of the queue, with its dependants, while its branch is another unfinished rollout's unlanded task's or an earlier task's of this queue; a started carried task stays, with a WARN.

11. **Lane entries that run no mark-integrating re-enter with no check.** A *Lost call* resume of an integrate call, a room-stopped integrate call's resume, a merge-hold release (on Lachy's go-ahead or a heartbeat's `review required:` re-run), and the RACE revert re-enter the lane with no origin-lane check. Each holds a lane this rollout was granted (a live call's handle, or Lachy's go-ahead) or restores a red `main`. These overlaps arise only after the rollout's lease stopped reading fresh, or after its merge hold freed the origin lane. If another project's merge moved `main`, merge-task exits 3 and step 3 applies the origin lane; the residual is two holders for one Integration, plus merge-task's seconds-wide window, whose collision is exit 5 and the RACE procedure.

12. **The Reflection reads a yield as a pause inside one Integration.** score.py's holdings: a `lane-freed release=origin` ends a holding, and the same task's next holding, with no merged, set-aside or from-file carried line between, continues that Integration (`integrations` counts it once; its conflict and integrator path come from its last holding); the gap is no lane busy time. ledger.py prices the gap as lane-bound, never stalls; grades.py's lane hours leave it out.

13. **Status and repair read a yield.** `reconcile-rollout.py status` gives an integrating task whose Run record's last lane line is an origin yield `originWait {origin, since}`; status renders `waiting on the origin lane (<origin>) since <since>`, and repair classes it **origin lane wait**: nothing with a lead live, § 4's hand-off with none, never a hand-back or a set-aside.

## Considered and rejected

- The note's suggested name, `<toplevel>-rollout-<slug>`: it does not end in `-rollout`, so every clone prefilter would change.
- Never refusing a caller that already holds its own lane: a Base-moved re-run would then keep the lane from a waiter forever.
- A merge hold that keeps the origin lane: Lachy's approval could then hold every other project's merges for hours, while a merge meanwhile only makes the held task re-integrate.
- An `integrating:` age cap in place of the lease rule.
- A waiter kept by its lease alone: a live lead that stops trying would block the lane forever.
- A shorter heartbeat while waiting: a full lead turn every few minutes, where the origin wait costs nothing until the lane frees.
- An origin-lane check at the re-entry sites (decision 11): a merge-hold release that waits ends in merge-task's exit 3 and a re-integration, a second approval under `--gated`.
- A per-key knob rule (decision 9).
- Counting each origin holding as its own Integration: it inflates the set-aside and conflict rates the Reflections tune on.

## Consequences

- A per-project clone sits idle after its rollouts finish; its only cost is disk.
- A waiting lead learns the lane is free only from its own reads: its origin wait (about one 20 s poll plus its turn) or its heartbeat (at most 20 minutes). A waiter that stops trying idles the lane for at most 30 minutes, a crashed holder for at most 45.
- A gated or review-required task may need a second approval when another project's merge lands during its merge hold.
- A first-time per-project clone still asks ADR 0042's question, so under orient-all its fork stops and Lachy runs `/thread:schedule` once.
- A root-contest loser goes in the next estate pass, never a later batch of the same one.
