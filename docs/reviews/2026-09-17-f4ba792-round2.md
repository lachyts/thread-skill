## Correction — 2026-09-21, from the review of this doc's own fix batch

The clean-room round on `07ddc75`/`e55ab3` (see
`docs/reviews/2026-09-21-07ddc75-e55ab3.md`) found this disposition table wrong in two places.
Recorded here so nobody reads the table above and believes it:

- **Finding 7's row overstated the fix.** It said "The doubling is gone … the template's worst-case
  line is therefore still correct and needs no caveat." Both halves were wrong. The capped implement
  layer spends `n + floor(n/2)` ≈ **1.5 × max_iterations** against an uncapped run's `1 + n` — reduced
  from 2x, not eliminated, and still *more* than uncapped for n ≥ 4. Worse, at the template default
  `max_iterations: 3` the halving handed the retry exactly **1** iteration, and a 1-iteration
  `ralphLoop` blocks without ever re-running the verifier — the "one verifier pass and zero fix
  iterations" degradation ADR 0016 §1 exists to forbid. Fixed 2026-09-21 (budget floors at 2), and
  `rollout-template.md` § Resource budget now documents the 1.5x.
- **Finding 8's replacement comment asserted a false invariant.** It claimed "every builder reads
  `st.capSuppressed` directly". No builder reads it — they derive framing from `st.escalated` and
  `terminalTier(st)`. Corrected 2026-09-21.

A third defect in the same area was pre-existing and missed by this round entirely: `effortTier()`
keyed off the `capSuppressed` *event* flag, so a non-plan-gated capped task ran its terminal first
pass at the LOWER effort row — contradicting ADR 0016 and `execute/SKILL.md:83`. Also fixed
2026-09-21, with Scenario F added to cover the template-default shape.
