## 5. Findings

(one line per FAIL/KNOWN, with the vault task it became)

- **Verb 1, checklist wording (not a plugin defect):** bare `/thread:open` in a fresh session falls through to `list`; creation needs `/thread:open <slug>` (or a conversation with thread shape). The 2.6.0 re-run should say `/thread:open zz-thread-e2e`.
- **Verb 2, gather spec nits (PASS, low):**
  - `--light` promises "the body stays byte-identical", but the mandatory backlink rewrite edits a body when a sibling links an old slug (t3's `[[zz-thread-e2e-t1]]`). Gather's Verification step 3 ("bodies byte-identical (diff)") would fail on any fixture with an intra-set link. Fix: "byte-identical except backlink rewrites".
  - Gather cites `add-task.md § Phased tasks`; there is no such heading. The rule is a bullet under § Step 4 (`add-task.md:101`). Fits the brief's p1-1 references contract.
- **Verb 3, split/gather numbering nit (PASS, low):** split infers phases as dependency layers from **0** (`split` § 3), while gather continues from `N_max` so a fresh project's first phase is **P1**. The same empty project gets `p0` from split and `p1` from gather. Pick one base.
- **Verb 6, status has no in-flight-wave case (FAIL-shaped, medium):** `/thread:status` § 4's next-action list covers paused / all done / "approved PRs awaiting merge / cursor behind" / blocker-drift / nothing dispatched. A wave running right now fits none of them, and "cursor behind → re-run `/thread:execute`" is the nearest. Following it mid-wave re-dispatches the running task, because `resume-filter` only excludes done/review/merged/gate-pending, not `in_progress`. Status can't see the Workflow run, but it can see `wave_K_dispatched` set with `wave_K_merged` unset and the task `in_progress` with an `owner:`. Fix: add "wave K in flight (dispatched, not merged, tasks in_progress) → wait for the run; check `/workflows` before any resume".
- **Verb 5, ceremony nit (PASS, low):** execute § 4.5 step 5 says to archive the rollout with `git mv`, which fails on a rollout note that isn't committed yet. That is the normal state, because the vault's fixture and real notes wait for the 11am sweep to commit them. Fix: "`git mv` when tracked, else `mv`; commit the moved note by pathspec".
- **Verb 7, repair can't resolve `in_progress` + merged PR (FAIL, medium) → vault task to file (S2):**
  - What happens: a task note at `in_progress` whose PR is verified MERGED is stranded. It can end up there through an out-of-band merge before reconcile, a vault revert or sync clobber, or a hand edit.
    - repair § 2 classifies drift as only `review-blocked`/`blocked` + MERGED.
    - `resolve`'s `RESOLVABLE_STATUSES` excludes `in_progress`. The comment "open/in_progress means the task never landed" is false once the PR is verified merged.
    - `mark-done` takes `review` only.
    - `resume-filter` treats it as still-to-dispatch.
  - Consequence: following repair § 4 re-runs non-idempotent work on top of the merged result.
  - Also, status § 3's drift flags don't cover `in_progress` + MERGED.
  - Fix:
    - Add an `in_progress`/`open` + MERGED row to repair's drift class and to status's drift flags.
    - Let `resolve` accept `in_progress` when the caller passes a verified-merged PR, or add a `--merged-pr` guard. Keep refusing `open`/`in_progress` with no merged PR.
  - Dedup: no existing `thread-*` task covers it.
- **Verb 8, checklist wording:** "dispatched to a sibling" can't hold when the honest recommendation is Keep going, which is next's own no-ceremony route. The 2.6.0 re-run should read "one recommendation; the chosen route runs (a sibling's logic, or Keep going)".
- **Verb 10, task-writer § 1.1 multi-match (PASS, low):** the `repos:` grep can match several project notes (here a sibling project sharing the repo; in real life a monorepo with sub-project notes). § 1.1 says "use that project note" and never says what to do with two. Fix: "more than one match → fall through to § 1.2–1.4 among the matches".
- **Verb 11, pickup never un-parks the thread (PASS, low):** stash sets the thread `state: parked` and moves its INDEX line (task-writer § 6), but open's `[[<task>]]` pickup has no step to set it back to `active`. The thread is live again yet still listed under Parked. Fix: pickup step 2 also sets a linked thread's `state: active` (and its INDEX line) when it reads `parked`/`paused`.
- **Verb 13, handoff `<home>` when the consumer lives elsewhere (low):** `<home>` is always the producer's CWD toplevel. S2 → S3 has to put S3's doc in thread-skill, because the fixture is deleted before S3 closes. Handoff has no rule for a consumer whose home differs from the producer's, or for a producer repo that is about to be destroyed. Fix: "write the doc in the consumer's launch-dir home when it differs, and name that path in the prompt".
- **Verb 12→13, handoff leaves an open stash/defer capture stale (low):** after defer then an immediate handoff, the Friday capture stays `open`, and its resume prompt ("run verb 13") is stale. Handoff never scans for open `thread`-tagged captures of the same thread. Fix: handoff (like pickup) closes, or refreshes to point at the doc, any open capture for the thread it hands off.
- **Verbs 10–13, thread-state churn (note):** stash set the thread to `parked`, pickup left it (verb 11 gap), defer set it to `paused`, and handoff has no state rule, so S1 set `active` by hand to match a live continuation. State transitions are specified per route rather than once. They belong in the P2 continuity-core shared lifecycle (brief p2-1).
